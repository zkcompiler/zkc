# Source language frontend

The lexer, the parser and the canonical printer of the zkc source language, written from the
reference of the language (`language/LANGUAGE.md` of the repository: §3 for the lexical
structure, §5 for the grammar, Appendix A for the rule identifiers), and its checker, which types the
bodies of functions and protocols and elaborates them to packages of the core. It is a library
of the package `zkc_compiler` (`lean/compiler`), beside the core, whose packages it emits and
whose `elaborate` and check of facts admit them; no library requires the frontend. `just test`
builds it and runs its test driver against the reference, the library in source and the worked
programs of the repository, and `just audit` audits its declarations and its imports
(`lake exe zkc-audit`) but does not replay them through the kernel: the frontend is the unproved
part of the compiler, and no theorem of the project rests on it, which the audit checks: it
refuses a module that it replays and that imports the frontend.

## Use

```sh
cd lean/compiler
lake build
lake exe zkc-syntax check <files>…          # per file: `accept` or `refuse <rule> <line>:<column> <message>`
lake exe zkc-syntax format <file>           # the canonical text
lake exe zkc-syntax dump [--no-spans] <file>
lake exe zkc-syntax generate <lines> <file> # the program of the measurements
lake exe zkc-syntax bench [--phase lex|parse|all] [--repeat <n>] <file>
```

```sh
lake exe zkc-check names [--library <dir>]… <files>…        # the refusals, or a summary
lake exe zkc-check resolutions [--library <dir>]… <files>…  # every entry of the table of resolutions
lake exe zkc-check instances [--library <dir>]… [--contents] <files>…  # refusals with chains, or a summary
lake exe zkc-check types [--library <dir>]… [--packages <dir> [--root <root>] [--scheme <name>]] <files>…  # refusals, then the package of each root
lake exe zkc-check run [--library <dir>]… --root <root> [--function <name>] [--role <role>]… [--messages <json>] [--seed <n>] --inputs <json> <files>…
lake exe zkc-check bench [--library <dir>]… [--repeat <n>] <files>…
lake exe zkc-check measure [--library <dir>]… --root <root> (--inputs <json> | --inputs-file <path>) [--repeat <n>] [--no-run] <files>…
lake exe zkc-check prove [--library <dir>]… --scheme <name> --statement <json> --witness <json> [--seed <n>] <files>…
lake exe zkc-check verify [--library <dir>]… --scheme <name> --statement <json> --proof <hex> <files>…
```

`check` prefixes each line with the file. A refusal is a value: the rule identifier, the span and
the message; where the reference gives a message for the case, the message is its wording.

A command that is not one of these, an option that the command does not take, or no file exits
with 2 and the usage. `zkc-check` reads the given files, then the module `zkc::prelude` and every module that a `use`
names and no given file has, from the first library directory that holds it: `zkc::a::b` is
`<dir>/zkc/a/b.zkc`. The library in source is `libraries/` of the repository; a worked program of
`examples/` also reads `examples` and `examples/support`. It reports every refusal in source order, the first of
each declaration, and exits with 1 when there is one. A check that runs out of a budget of the
compiler (the depth of the chain of instantiations, 256 requests) is incomplete, not refused
(SP10): it is printed as `incomplete <rule> <line>:<column>` with the budget, its value and the
request, and its chain; the summary starts with `incomplete`, and the exit code is 3. `types` prints, per root that is a
function, a relation, a law or a protocol, whether the core admits its package, refuses it,
whether it is typed only (a specification item over `rational` or a `spec type`, which have no
form in the core), or whether it waits for a form that is not typed yet, with the reason; then,
for every protocol typed, its table of sites: each core site with its event, its part, its name,
the iteration of each loop in sequence around it, and its place, and its specification
arguments, typed and not emitted (the site of the application, the port, the expression, its
type); then the obligation that each law typed leaves (the law at its instance, the module, the
place); `--packages` writes every emitted package as JSON (`zkc.core/0`), and the tables of sites
and specification arguments in `sites.json`. What `run`, `prove`, `verify` and `measure` run and what
`--packages` writes is a complete root or scheme: one that the run holds (its package admitted by
the core, its constructed program admitted and projected), when the run reported no error
anywhere in the program and left no check incomplete. A root that waits keeps no other from
being written or run. `run`, `measure`, `prove` and `verify` fail when the root or scheme they
name is not complete; `--packages` writes every complete root and scheme and lists the others
with why (refused, waiting, not checked), or, with `--root` or `--scheme`, writes those named and
fails when one is not complete. An error or an incomplete check anywhere writes and runs nothing.
`run` runs a function of the package emitted for a root (the root as `types` names it, or a
function of its package given by `--function`) on the inputs given as a JSON array, each
validated at the type it takes, under the core's model of the vocabulary's rows, and prints its
outputs or the reason it stops. Every run is under the core's limit on the work of reading: one
reading of a value builds at most 2^20 elements of collections. A run that reaches the limit is
not checked to its end: `run`, `prove` and `verify` print `incomplete:` with the limit and exit
with 3, as for a check that runs out of a budget of the compiler. A datum is
a number, or an array of data: a tuple, a record and a collection are arrays, an alternative of a
variant is `[its position, its payload]`, a `bool` is 0 or 1, an element of the quartic extension
is its four coefficients, a point of G1 is `[x, y]` or `[]` for the point at infinity. For a
protocol the inputs are one datum per port that is not `spec`, each validated once at the type of
its port; its package is projected to role programs, which the core's executor runs together,
each printed with its outputs, its stop, the limit, or `failed: waits for a message that is never
sent` when a peer stopped; `--role R` (repeated) runs only those roles, each alone, against the
messages that `--messages` gives as a JSON array of `[site, datum]` (a core site, as `types`
lists it) and the coins of an honest run of every role; `--seed n` seeds the draws and samples.
The `k`-th coin of a site under the seed is the value of the law of its type, as the core's
vocabulary defines it (`Vocabulary.lawValue`): a number modulo the order of a prime field, one
more than a number modulo the order less one for its units, a coefficient per number for an
extension (and the element one for its units when every coefficient is zero), the generator
times a number for G1, a tuple and a sized collection component by component. A type without a
law has no coin, and the run fails at its draw.
`measure` gives the cost of a root by phase: the checks of names and instances, the typing of the
bodies, the emission of its package (its operations and its bytes as JSON), the core's
`elaborate` and its check of facts, and for a protocol the projection to role programs and an
honest run (for a function, a run), with the peak resident memory and one row of all of it.
`types` also prints every scheme: constructed, with its prover and verifier, its statement and
witness, its proof identity and what the core makes of the constructed program, or waiting with
the reason (see *Schemes* below); with `--packages` it writes, for a constructed scheme `S`, its
package, its declaration and its constructed program as `scheme-S.json`,
`scheme-S.declaration.json` and `scheme-S.constructed.json`. `prove` runs the prover's program of
a constructed scheme on the statement and the witness, JSON arrays with one datum per port in the
order of the signature (as `types` lists them), its samples answered by the sampler of `--seed`,
and prints the proof in hexadecimal; `verify` validates the statement once and runs the
verifier's program on it and the proof, which is bytes and needs no validation, and prints
`accepted` when it returns, or `not accepted:` and its stop. For
`scheme Proof = Schnorr<G1>` of `examples/schnorr_example.zkc`, the statement is
`[[x, y], [x, y]]` (`base`, `point`) and the witness `[scalar]`.

## Schemes

A scheme `scheme S = P<σ>:` with the line `construction derived(M)`, `M` a module of the
catalogue suite `suite.merlin3.bls12-381.fr64be/0` (`zkc::suites::Merlin3Bls12381`), and the
layout `zkc::layout::canonical` (no `layout` line, or `layout canonical` without entries) is
constructed (§6.13, §7.8): the prover is the role that sends to the other online role, or the role
that does not draw, and a `prover` line is checked (SC3); the statement is the inputs that both
hold, in the order of the signature, and the witness the inputs that the prover holds alone; an
input that the verifier holds alone is refused (SC4); every draw between the two is of the suite's
challenge field `bls12-381.fr` (SC5). The package of the protocol instance gets the suite's
transcript and label types and rows (`start`, `absorb` at each type absorbed, `derive` at each law
drawn) and the layout's rows (`open`, `close`, `read`, `exhausted`, `put` and `take` at each
message type, over bytes). The declaration names them, its online roles are the two roles, and
its suite carries the proof identity: the SHA-256 of
`["zkc.core.proof/0", original, declaration, []]`, the original program with these rows, the
declaration whose suite carries no identity, and no stage parameter. The core constructs it
(`construct`: Fiat–Shamir, then serialize), its constructed program is elaborated again and
passes the check of facts, and it is projected to the prover's and the verifier's programs. After
serialize the prover's program runs alone and its first output is the proof; the verifier's runs
alone on the proof and the statement, and accepts when it returns.

Every other line (`context`, `samples`, `commit`, `grind`, `retry`, `pin`, `offline`, `ideal`, a
`layout` with `carry` or `recover`), a suite in source (`HashChain<…>`, which is neither
instantiated nor typed here), a catalogue suite without rows, the constructions `interactive`
and `authored`, a draw of another law that the suite decodes (`nonzero` of its field, `bool`,
`index<n>`, tuples and collections), and the generated members of a scheme (§8) wait, with the
reason. Of the schemes of `examples/`, three are constructed, admitted and run:
`Proof = Schnorr<G1>`, `Proof = Sumcheck<Fr, 10>` and `OrProof = Or<G1>`; `Proof = Gkr<Fr, 4, 2>` waits for its draw of
`[Fr; 2]`, and the others for a line or a suite in source.

### The schedule of the derived Schnorr proof, byte by byte

`scheme Proof = Schnorr<G1>` of `examples/schnorr_example.zkc`, for the statement `base = G`,
`point = 7·G`, the witness `scalar = 7` and the nonce
`k = 0x6b1a34d0f1e2c3b4a5968778695a4b3c2d1e0f00112233445566778899aabbcc`. Each role (the
prover P, role 0, and the verifier V, role 1) runs this schedule on its own transcript; the
constructed program applies, at each role, the suite's rows in this order, each after the literal
of its label. The labels are those of the core's Fiat–Shamir step: `[0, position]` for the
statement, `[1, definition, site, prover, verifier]` for a site, here of definition 0 (`Schnorr`)
at the sites 1 (`commitment`), 2 (`challenge`) and 3 (`response`). A label's bytes are its
numbers, each in eight bytes, least significant first. A value is absorbed as the bytes that the
layout writes for it: a point of G1 compressed (48 bytes, the ZCash serialization format of
draft-irtf-cfrg-pairing-friendly-curves-11, appendix C), a scalar in 32 bytes, least significant
first.

In STROBE-128, an `append_message` is the label as metadata (`meta-AD`), the length as metadata
continuing it, and the message as `AD`; a `challenge_bytes` is the label and the length as
metadata and a `PRF` of the length asked. The delivered copy of the challenge is not absorbed;
the statement is absorbed by both roles from their own copies. The proof is the bytes that the
layout writes for the prover's messages, in order, and nothing else (80 bytes):
`R ‖ z` = `8b184d6d…d3d5192c` `7ed36654…96adbb35`. Operation 7 changes no byte of the proof: the
proof and the challenge depend on operations 0 to 6 only.

The proof identity is the SHA-256 of a text of 2,583 bytes: the original program of the package
(the types `bls12-381.g1`, `bls12-381.fr`, the transcript and the label of the suite; the rows
`law.uniform`, the group and field rows of the protocol, the suite's `start`, two `absorb` (at G1
and at `bls12-381.fr`) and `derive`, and the layout's six rows with `put` and `take` at G1 and at
`bls12-381.fr`), the declaration
`["declaration",0,0,1,["catalogue",["nominal",2],3,6,[7,8],[[0,9]],[]],["canonical",…,10,11,12,13,[14,15],[16,17]],[0,1]]`
and `[]`. A Python recomputation from the JSON that `types --packages` writes gives the same
digest.

The test driver checks this proof two ways: it equals the bytes committed in
`Zkc.Tests.Frontend.Schemes`, and it equals the proof that the independent replay
`scripts/replay_derived_schnorr.py` computes (Python, the standard library only: Keccak-f from
FIPS 202, STROBE-128, Merlin 1.0, G1 and its compressed form from their definitions, and this
schedule; it checks itself against SHA3-256, Merlin's conformance vector and a published vector
of the ZCash format first; the driver needs `python3`, and a replay that does not run or gives
other bytes fails the run). The
core's tests check Merlin against its published conformance vector, and the layout's reader of G1
against the published deserialization vectors of the ZCash format in
`github.com/ethereum/bls12-381-tests` (`case08_deserialization_G1` of `main.py`).

## Tests

```sh
lake test
lake test -- --trees
```

The driver reads the repository from the directory of the package: the reference of the language
and its conformance tests in `../../language`, with the independent conformance suite (cases and
`expectations.json`) in `../../language/conformance/independent`, the library in source in
`../../libraries` and the worked programs in `../../examples`. A directory that is missing stops
the driver with an error. It checks:

- every file of `libraries/` and `examples/` parses, and the printer keeps its tree;
- formatting keeps a program: 36 programs of `Zkc.Tests.Frontend.FormatCases` (a function at the
  top level, in a module and in a module that implements an interface, with no parameter or
  one, the result `()` or `nat`, and a body of `return` alone, an `if` expression or a guard
  then `return`) and their canonical texts are admitted; formatting a canonical text gives it
  back; and a canonical text has the declarations of its program, of the same kinds, and the
  same instances holding the same types, as `zkc-check instances --contents` prints them. Every
  file of `libraries/` and `examples/` keeps its outcome, its declarations and its instances
  after formatting;
- every program of `conformance/`: a test whose expected refusal is a lexical or grammar rule is
  refused by that rule, every refusal names a rule of its test, and the refused tests are the
  list in `Zkc.Tests.Frontend.Reference`;
- programs for each rule of §3 and §5, the contextual words of §3.4 used as names, the forms of
  the newest forms of the reference, the byte-level rules (line ends, UTF-8, Normalization Form C, tabs),
  precedence, both spellings of each mathematical form, and the canonical printer;
- a generated program of about 50,000 lines;
- the check of names over the tests of layer A: a test whose refusal is by a rule of names (NL2,
  NL3, NL4, NL7, NL10) is refused by that rule at the line listed in
  `Zkc.Tests.Frontend.NamesReference`, or is listed there as waiting for typing; no other test is
  refused, except `L-ALG3`, which the check refuses by its own rule (SP3); every module of `libraries/`
  as a root,
  every worked program with its example file, and the generated program resolve, with every
  module they reach. In every given file without a refusal, every `Path` that the dump of the
  tree shows has a resolution. Every program that a check compiles has a lowered form that says
  one thing at each place: two nodes that disagree at a place are refused as a defect;
- the check of instances over the tests of layer A whose names resolve: a test whose refusal is
  by a rule of this check (NL1, NL9, SP3 to SP6, SP8, SP11, GR5, TY2) is refused by that rule at
  the line listed in `Zkc.Tests.Frontend.InstancesReference`, or is listed there as waiting for
  typing with the reason; no other test is refused; every module of `libraries/` as a root, every
  worked program and the generated program form their instances, except `stark`, which is
  refused by NL9 exactly at the asset module of `support/fibonacci.zkc`, a withdrawn form;
- the typing of bodies over the tests of layer A whose instances form: a test decided by the
  typing of a body is refused by its rule at the line listed in
  `Zkc.Tests.Frontend.TypingReference`, or its roots are admitted by the core or typed only; a
  refusal by a rule that is neither the one a test expects nor its stated alternative is a
  contradiction, listed, and a failure unless the table of known contradictions (empty) gives its
  reason; a test whose roots wait for a form that is not elaborated yet (`attempt`, the oracle
  events, layer D, a law that is a tuple or a collection, a generated member, a row at a module
  argument) waits, with the reasons of its roots; the table of the waits that this check leaves
  is empty; a test of acceptance that no root reaches is listed apart; every module of
  `libraries/`, every worked program and the generated program type, except `zkc::layout`, whose
  `canonical::read_natural` its own note says is to change, recorded in
  `Zkc.Tests.Frontend.TypingReference`; the default instances of `prelude`, `option`, `algebra`
  and `sequence` are all admitted, no package emitted is refused by the core, and every function
  emitted passes the core's check of facts;
- every public function of `zkc::sequence`, at instances over `koala-bear` and `bls12-381.fr` and
  at size 0 where its `where` allows, runs on inputs and returns the value that a plain function
  over lists and numbers, written in the test, computes; `get` and `slice` stop `refused` outside
  their range; no run stops `undefined`; the function members of the sorts at `koala-bear`, its
  quartic extension, `bls12-381.fr` and `bls12-381.g1`, and the arithmetic of the extension and
  of G1, run from source against values stated in the test;

`--trees` runs only the suite of the typed trees of the protocols of a corpus (each module of
`libraries/`, each worked program with its example file, the generated program, every test of
layer A and every case of the independent suite that the frontend accepts, the test modules of
the generators and the programs of the run tests): the invariants of the trees, and the second
reading (`Zkc.Tools.Frontend.Reading`), which evaluates the tree of each protocol root role by
role and compares what each role does with the run of its emitted package, by the keys of the
events (`Zkc.Tools.Frontend.PackageRuns`). It runs under the core's model of the vocabulary's
rows only, on inputs and coins drawn from four seeds, and draws no boundary values (zero, one,

one. A root whose package has a row that the model does not compute, such as the rows of
circuits (`circuit.values`, `circuit.layered`) in the present corpus, or whose run would be too
long, is counted as incomplete and is not compared: the suite notes these counts and does not
fail on them. A reading that is observed to differ, or that breaks off, is a failure. The suite
takes about 24 minutes.

For every program that parses, the printer is checked three ways: the printed tree parses back
to the same tree (up to spans), the canonical text parses to the canonical tree, and formatting
the canonical text gives it back byte for byte; the comments are kept.

## Readings of the reference

Where the reference leaves a choice, the code takes the reading marked in its comments:

- The parser refuses what §3 and §5 refuse, including the restrictions stated in prose under the
  productions (a kernel attribute only before a body, `spec` only before a natural parameter, a
  specification argument after the others, `using` not after `external(…)`, `= external` only
  on a `spec def`, one expression as the body of a law or a relation). A form with no
  production is refused by the rule whose message the reference gives for it (`EV2`, `RM1`,
  `CT1`, `HO3`, `NL9`, `SC5`, `OR3`, `TY13`), otherwise by `GR`. A rule of §6 that restricts a
  form the productions admit is left to the checker: an event in a `def` parses (FN1).
- `sum([e for x in D])`, `product`, `all`, `any` on one comprehension without a condition, and
  `inner(a, b)`, are the named spellings of the mathematical forms; any other call of these
  names is a call.
- A single name after `case` is the `Pattern` alternative; whether it names an alternative of a
  variant is for the checker.
- Breaking a line longer than 100 characters: the widest of the shallowest brackets that hold a
  comma is broken after each of its commas; a `;` does not break.
- Blank lines: one between top-level items, except between consecutive `use` items, which keep
  the source's choice; elsewhere one where the source has one or more.
- Comments are not in the tree. The formatter places each before the first construct (item,
  member, statement, case, clause, scheme line) that follows it, at that construct's
  indentation: a comment at the end of a line or inside a bracket moves to its own line.
- The formatter removes the annotations of FM2 that the text decides (`else reject`, `-> ()`
  except on a `def` without parameters in the suite of a module, `#[site(x)]` on the binder `x`,
  a role mapped to its namesake), writes one role without parentheses and roles in roster order
  inside a protocol, and prints a body of `return e` alone as an expression body, except
  `return ()`. The rows of FM2 that compare an annotation with what the checker computes are
  kept.

## Readings of the reference for names

- A path of a `use` is a module path followed by names; the longest prefix that names a module of
  the program or of the library is the module. Nothing else names a module by its path: a path
  outside a `use` starts with a name in scope (NL4: nothing else is in scope without `use`).
- Two sibling suites may bind one name; a suite does not rebind a name of an enclosing suite
  (NL2). Two events of one definition with one name are left to the rule of sites (EV3), which
  the tests of layer A name for them.
- A single name that no scope binds, where a value or a pattern after `case` stands, is recorded
  as a bare alternative when some variant of the program has an alternative of that name, and
  typing refuses it by NL3 when the expected type has none; otherwise it is refused (NL3). A
  single name after `case` binds unless some variant has an alternative of that name.
- A declaration or an import with the name of a function of the fixed table hides the function
  in its module, as a local name does; NL10 covers the names that the prelude binds publicly.
- A member reached through a static parameter, `Self`, or a type or module member of one is
  checked against the interfaces that the text declares for it, and refused by SP3 when none of
  them has it; a `where` that equates it with something other than such a path leaves its members
  to the instance. A member of a declared type is left to the instance.
- `Self` in a module that implements an interface is that module (SP8: a member repeats the head
  the interface writes with `Self`).
- In a contract, a clause `… at i` whose loop the protocol does not have is left to SX6, and the
  results are in scope in `ensures` and on the right of `reduces` only (SX5).
- After `stage`, `statement` and `decisions` in a goal a single name is a word; after `clause` a
  label, after `corrupted` a role (GL2); which word, label or role it may be is decided with goals.

## Readings of the reference for instances

- A sized collection of elements of a `Group` is a `Group` with the scalar of its elements
  (TY11); its `Order` is the number of its values, the order of the elements to the power of the
  size.
- A module bound to the vocabulary or to an asset has the members that its row or its asset
  gives; a member that they do not give is not known here, and what reads it is not evaluated.
  A row of the vocabulary that implements an interface implements only it: a module bound to the
  row names that interface (SP8).
- A size is built with `+`, `-`, `*`, `/`, `^` and `log2( )`: `%`, `++` and a prefix `-` are
  refused in a size (TY2).
- The package of a program is its given files: its roots, its comments `// instantiate:`, the
  default instances of its public declarations and the checks of its declarations. A library
  module that a path reaches is instantiated where something reaches it; given as a root, it is
  its own package. A type or a module bound to the vocabulary or to an asset is checked as NL9
  states when it is instantiated.
- A default module is the first module of the program, the given files first, that names every
  interface of the bound; its static arguments that the bound does not determine take their
  first default value. Several upper bounds of a natural give the smallest; `n < T` gives `T - 1`.
- A refusal of a bound is made at the bound in the declaration; the chain names the instance and
  the reference that asked for it.
- A function member is defined by its binders (`def f(x…)`), not by a `def` with types (SP8).
- Steps 3 and 4 of SP6 also match an unsized collection and a tuple component by component; a
  parameter found twice with different values is a conflict that typing reports at the argument.
- What a body contains (calls, applications, static arguments, sizes, members) is checked by the
  typing of bodies at instances, where a static condition decides which arm is reached.

## Readings of the reference for typing

- A body at an instance is elaborated to the typed tree; the core checks its facts, the
  definition alone with its callees as headers; a package is emitted from the trees per root.
  A statement that elaboration refuses is an error node, and the statements after it are
  elaborated, so that every refusal of elaboration of a body is reported; of the facts, what
  stands before the first error node. A caller of a refused callee is not typed further.
- `a <= b` is `not (b < a)`, `a > b` is `b < a`, `a >= b` is `not (a < b)`, `!=` is `not` of
  `==`. The comparison of a field element with the literal `0` is the domain row
  `field.is_nonzero`.
- A literal of a ring or a field is the core's literal of its nominal type (the numbers its model
  reads, the row `field.literal` or `ring.literal`); `0` of a group that is no ring is the row
  `group.zero`, of a sized collection of group elements `seq.fill` of it; a number against an
  `index<s>` is a `fin` literal. A static natural used as a value where a ring is expected is the
  number it evaluates to (TY2, TY6).
- `nonzero<F>` is the nominal row `nonzero` at the type `F`. Its widening to `F` is the row
  `field.from_nonzero`. The units are closed under `*`, `/`, `^` and prefix `-`: a quotient,
  product, power or negation of units is a unit (needed by `batch_inverse` and by the test
  `R-TY6c`).
- A row on a type of the vocabulary takes that type as its static argument; a row on collections
  takes the element type and, for a sized collection, the size. A `def` bound to a row is that
  row at the written static arguments of `primitive(…)`, or at the instance's values when none
  are written; a function member of a module bound to a row is the module's row, or
  `<row>.<member>` when its interface has several function members.
- `and` and `or` are the boolean operations when the right operand applies no operation with a
  domain and calls nothing that can stop; otherwise a local `if` on the left operand whose other
  region returns the literal `false` (`true` for `or`), which the core reads as the conjunction
  (disjunction) and which gives, taken true (false), the facts of the left operand only. The
  checker gives such a value the same facts. So that every operand's facts reach what needs them
  (TY9), `(a and b) and c` with `a and b` a local `if` is `a and (b and c)`, `not (a or b) and c`
  is `not a and (not b and c)`, and a condition with an `and` or an `or` that is a local `if` is
  taken one operand at a time: the arm of a condition that does not hold then stands once per
  operand.
- `==` without a row or a home `equal` is structural: componentwise with `bool.and` for tuples and
  records; for variants a result that starts `false`, set by a `match` on both values where they
  have the same alternative; for collections of elements without a row a result that starts
  `true`, carried by a loop (with an inner `if i < length(ys)` for collections of run-time length,
  and the comparison of the lengths); `seq.equal` for collections of field or group elements.
- A function returns one value of its result type; `()` is the empty tuple. A `linear struct`
  is used exactly once; any other record is copied freely.
- The index of an empty range has no value: every check through it holds (TY11: the element is
  typed once, also when the range is empty). A `∑` of naturals over a static range whose term
  mentions the index is written one term at a time, from `0`, up to 4,096 terms, so that its
  range is the sum of the ranges of its terms (TY8); otherwise it is a loop that carries the sum,
  whose range over a static count is the count times the bound of its term. A `∏` of naturals has
  no upper bound: TY8 gives it none, nor does the core to a carried product. A fold written one
  term at a time starts from the start of the form and combines each term in turn.
- The index of a loop over a static range is typed as a natural; where it stands in a static
  position (a size, a static argument, a static name, a tuple position, a bound of a slice), or
  where a `mut` name changes type (a stepped loop), the loop is its iterations in sequence: the
  body typed and emitted once per iteration, the index a literal, each `mut` name at the type the
  iteration before left it. A name the loop collects is then the collection of its values when
  they have one type, their tuple otherwise (TY16).
- `[]` checks against every collection of size 0 and every unsized collection; alone it is
  `[(); 0]`, which joins any collection, and `++` takes the element type of the other operand. In
  inference it gives the size 0 to a parameter `[T; s]` and nothing to `T` (SP6).
- A range whose start exceeds its end, or whose order is not known, is refused by CT6 (the test
  `S-Z1`), with the message of TY10.
- In inference (SP6), a type found twice for one parameter agrees when one widens to the other:
  the parameter takes their join (the library's `coset.extend` passes a `nonzero<F>` where `F` is
  inferred).
- A written argument that needs an expected type, and whose parameter's type mentions a
  parameter that inference has not solved, is typed after the inference, after the other
  arguments; the arguments are evaluated in the order written. The fields of a construction are
  evaluated in the order written, whatever the order of their declaration.
- A `match` case that is a name and no alternative binds the value and covers the alternatives
  that have no case of their own.
- `:=` on a name that is not `mut` is refused by GR3.
- A definition generic over a module parameter (a `def`, a `spec def`, a relation, a member
  definition whose module has one) is typed twice at each instance, the opaque typing first, and
  stops at the first refusal; SP7 item 8 orders the opaque typing second, SP12 first. In the opaque
  typing the parameter stands for its module with the interfaces its bound requires, and each type
  member of them that no `where` in scope equates with a type is a fresh type, one per application,
  with the sorts of the bound the interface writes on it. An operator, a form, `==` and a dot call
  on a fresh type is the row of its sort where the sort has one, otherwise the member of that name
  of the interface; the place is recorded. In the instance typing the type member is its
  definition, and at each place recorded the operator is the call of that member of the module the
  parameter stands for; a callee is its ordinary instance there (a callee that the opaque typing
  reached with the fresh type is checked at it). The instance keeps those places with its code.
- A row of a sort at a fresh type has the type of the row at the representative of the sort, the
  fresh type in its place; the code of the opaque typing is not emitted.
- A `spec def` or a relation is typed by the elaborator with `rational` and `spec type`s and calls
  of specification functions; one whose types and operations have a form in the core is emitted as
  a specification-only function and admitted, a relation as a function to `bool` over its
  statement and witness (the core reads no `relation` definition), a header bound to the formal
  library as an `opaque` definition whose name carries the external name; any other is typed only.
  A specification item reads its specification-only parameters at 0, 1, 2 and 3 without a goal.
- A law of an interface is typed at every implementing module instance the checker reaches, with
  `Self` that instance, and a law of a module at each instance of the module's scope, both at the
  default values of the law's own parameters where its `where` holds; each typed law leaves an
  obligation and is emitted as a specification-only function where it has a form in the core.
- In inference a type member of the module that `Self` or a known module parameter stands for is
  its definition (SP8, TY3), its written arguments giving the member's own parameters; two
  applications of one fresh type member are matched argument by argument (SP12).
- A pattern inside a payload covers every value of its type: a tuple of such patterns, and the
  alternative of a variant with one alternative, whose payload a `match` of one arm takes out.
- The home module of a type of the vocabulary, for a dot call, is the module of the first
  declaration that binds its row.
- A loop of no iteration is a loop of the count 0.
- A choice whose condition is such a local `if` is one local `if` on its value; when an arm needs
  a fact of the right operand, which the core does not give, the choice is made one operand at a
  time (`if a: (if b: S else: E) else: E`). So is the condition of a comprehension, with a
  negation moved inward (`not (a or b)` as `not a and not b`). A guard on `a and b`, or on
  `not (a or b)`, is a guard on each operand, in order: each has the facts of those before it,
  and the suite after it the facts of all.
- A function member of a sort applies its row of the vocabulary, whose type must be the member's
  type in the interface at the type; otherwise the function waits.
- A restricted row names its domain row (`field.nonzero` names `field.is_nonzero`), which the
  package numbers before it.
- A package is emitted per root: the roots, the instances of `// instantiate:` comments and the
  default instances, each its own. Types, records, variants and rows are numbered in the order of
  first reach; a function after the functions it calls. The captures of a nested region are its
  free values and the values that the facts it relies on mention, in the order of their numbers.

## Readings of the reference for protocol bodies

Each reading is followed by the alternative it rules out.

- The protocol instance that a `scheme` names is a root, like a comment `// instantiate:`, also
  when the scheme waits. *Otherwise* a program whose protocols only a scheme instantiates
  (`chaum_pedersen`, `inner_product`, `spot_check`) would type nothing.
- The holders of every expression and the roles that compute every statement are computed on
  the source before anything is emitted (HO1, HO2); inside a choice or a loop only its
  participants run, so a copy of a closed binding at another role is never used there and is not
  made (§7.5 removes such a copy). *Otherwise* a role that does not run the region would compute
  in it.
- A statement computed by several roles is typed at each with its own facts; when it types at one
  and fails at another by TY5, TY7 or TY8, the refusal is TY4's, naming the role that lacks the
  fact. *Otherwise* the refusal would be the bare one of the role that failed.
- A role that must compute an expression it does not hold is refused by HO1 (an update, an
  argument of an application, a result; the tests `M-FRA12`, `M-SUM7`), and so is an expression
  that no role can form (`T-H1` accepts HO1 or HO2); an `@` beyond the holders is refused by HO2
  (`T-H3`). *Otherwise* all by HO2.
- The item of a loop is held by the roles that hold both bounds of its range, or its collection
  (CT3); a value it collects is computed by its holders among the participants, and makes them
  act as a binding does: not when it is closed and cannot stop. *Otherwise* the index would be
  held by the participants only, against CT3.
- A `for` is a `repeat` of its participants: a static count, or one count per participant whose
  maximum is the largest `hi(b) - lo(a)` among them (CT4); the iteration number of each
  participant is the first input of the region, plus the start of the range by that role; each
  updated `mut` name is carried per holder; the collected values come first among the region's
  results and the operation's, then the carried ones. A run-time bound without a static bound at
  a participant is refused by CT4; an unsized collection by CT5.
- A loop whose state changes type, and a loop whose index is static in its body, is its
  iterations in sequence (the first of the two forms of §7.5): each iteration typed with the index
  a literal; each occurrence of an event has core sites of its own, the first iteration's those
  of the text, and the table of sites records the iteration of each. *Otherwise* one `repeat`
  over an unsized carrier, whose length per iteration a fact of the core would give; the
  measurement of `Sumcheck` found code linear in the rounds small at the sizes programs use.
- After a loop of no iteration a collected name is `[]` at the type that the body, typed apart and
  forgotten, gives its expression, or `[]` of any element type when the body does not type
  there (a stepped loop at a count of 0, as `Reduce` with no round).
- A `match` of a protocol body is a choice on the alternative of the matched value at each
  participant, the core's `case`; the region of an alternative binds each participant's copy of
  its payload.
- A specification argument of an application is typed against its port at the callee's
  instance, in a view that has the names of every role, with the rules of specification
  expressions, and is not emitted; the tool lists it with the site of the application and the
  port. *Otherwise* it would be typed at one role, whose names it might not all have. An argument
  that names no specification port of the callee is refused by RM3.
- A protocol generic over a module parameter is typed twice, the opaque typing first, as a
  function is (SP12). A module that a parameter stands for there has no laws of its own to type;
  a type member of one of its type members (`E::G1::Scalar`) is not evaluated, and the protocol
  waits for it.
- After a choice, a `mut` name whose types at the ends of the arms have no join is refused by
  TY10, as in a function.
- An application gives every specification-only parameter of its callee, except those of a scope
  that the caller shares with the callee, which are the caller's own (SP11); a deployed static
  argument that reads a specification-only parameter is refused by SP11 where it stands.
- Events are numbered in the order of the text, depth first, the arms of a choice in order and the
  body of a loop once; a send to several receivers has a part per receiver, each a core site of
  its own. `#[site(…)]` names the site of a tuple pattern.
- Linearity: any read of a linear name in deployed code is a use, a read of a field included;
  the right operand of `and` and `or` is a path of its own; both arms of a static `if` are
  checked; `[v; s]` is a loop over the copies of `v`. *Otherwise* a field read would leave the
  value owed. A type parameter without the bound `linear` that a linear type instantiates stays
  refused by SP3, as the check of instances found it.
- A test of acceptance in which no root reaches a body (`T-L1`, `T-L11`, `R-SP7d`, `L-ALG5`) is
  neither accepted nor refused by the typing of bodies; it is listed.
- A role that waits for a message that no role sends, because a peer stopped (GU3), is ended by
  the core's executor as failed, `waits for a message that is never sent`; the tests read it
  as blocked. A message or a challenge changed on the way is a run of each role alone against
  what the others send: the coins of an honest run, with the challenge changed where it is the
  one changed, and the messages that each role sends against them, with the message changed
  where it is the one changed. A challenge changed on the way reaches only the prover; in a run
  of one round no message of the prover follows it, and the verifier, which reads its own copy,
  accepts.
- A law that is a tuple or a sized collection of laws is one sampling row, the vocabulary's
  `law.uniform` at that type; the model samples it component by component. *Otherwise* the tuple
  of the rows of its leaves (§7.5), which the core's `draw` and `sample`, one row each, do not take.
- Admission of a package is the core's `elaborate` and its check of facts for every function and
  every protocol. A region of a protocol body captures, with its free values, the values whose
  facts its operations rely on, as a local region does.

## Readings of the reference for schemes

Each reading is followed by the alternative it rules out.

- The catalogue suite's interface in source (`zkc::construction::Suite`: `start`, `absorb`,

  (draft-irtf-cfrg-pairing-friendly-curves-11, appendix C). *Otherwise*
  nominal types for them, opaque to the program; bytes are what a proof is, and the verifier's

- A label's numbers are each written in eight bytes, least significant first: the suite's own
  encoding of the label it is given, which is not a value of the canonical layout. *Otherwise*
  one byte per number, which would not separate a definition or a site above
  255, or a text.
- The `start` row is `Transcript::new(<the suite's row>)` and `append_message(b"identity",
  <identity>)`; the bytes of the identity are its 32 numbers.
- A challenge is `challenge_bytes(label, ChallengeUnits)`, 64 bytes for this suite, read most
  significant first modulo the order of `bls12-381.fr` (the suite's `fr64be`). A draw of another
  law that the suite decodes waits: its decoder is not implemented (the reference does not state
  how `nonzero`, `bool`, `index<n>` and the composites are decoded by this suite).
- The proof identity is computed over the declaration whose suite carries no identity (`[]`),
  then written into it, since the catalogue suite carries the identity itself; the stage
  parameters are `[]`, the suite and the layout being in the declaration. *Otherwise* the
  identity would depend on itself.
- The reader of a point of G1 accepts exactly the bytes that the writer writes (the three flags,
  `x` below the characteristic, a root of `x^3 + 4`) for a point of the subgroup of order `r`; a
  point of the curve outside the subgroup is refused. The other types are written as the core's
  canonical layout writes them (`docs/spec/core/stages.md`, *The canonical layout*), and no value
  is written as another: `index<n>` in the least number of bytes `k` with `n ≤ 256^k`, least
  significant first (`bool` in one byte), a `nat` as unsigned LEB128 in its shortest form, a
  collection without a size as its length as a `nat` and then its elements; a number not below
  its bound, a natural in another form and an element not below the order of its field are not
  read. A proof of field and group elements only, as those of Schnorr, Sumcheck and the OR
  proof, is the same bytes as before. One reading of a value builds at most 2^20 elements of
  collections (the core's limit); a verifier on a proof whose lengths ask for more ends with the
  limit, not with `reject`, and the proof is not checked to its end.
- The verifier accepts when its program returns (SC4: no line states an acceptance). *Otherwise*
  its first `bool` output decides.
- The online roles of the declaration are the two roles of the protocol; with an `offline` or
  `ideal` line the scheme waits.
- A suite in source and the layout of a `layout` line are named, not instantiated, when the
  scheme waits for them: instantiating `HashChain<…>` types `zkc::layout::canonical`, whose
  `read_natural` the reference's note marks as to change, and its refusal would be
  reported for every program with such a scheme.

## Readings of the reference for the independent suite

- An immutable name has, at each role that computes it, the facts of its right side at the
  binding: its range, its size, that it is not zero (`j = i + 1` with `i: index<4>` returns as an
  `index<5>`). *Otherwise* only types, guards and loop bounds give facts. A slice whose bounds are
  not static has no static size, and no fact of its length is made: the core's check of facts
  could not justify one (`a[0..length(a) - 1]` sliced again by `length(t) - 1` is refused).
- An instance of an implementing module types every function member, called or not, at the
  default values of the member's own static parameters where the member's `where` holds (SP7
  item 7); a module without static parameters is a root.
- An exponent is inferred only for a base of at least 2 (SP6 step 4); with a base of 0 or 1 the
  equation is set aside.
- A reserved word where an expression or a name is expected is refused by LX9, with its message.
- The update of a `mut` name without a written type is typed without an expected type: the name
  has the type of its last update (TY10), so SP6 step 6 has nothing to match (`M-GKR1`).
- `index<0>` has the empty range: it has no value, and every check through it holds.
- The suite's citations and the frontend's rules differ in three places, taken as equivalent:
  NL6 for an operator case that cites §3.5 or SP12; TY7 for a case that cites TY5, TY8 or TY9;
  TY8 for a case that cites TY5 or TY9. The open questions are checked against the readings of
  the register of findings: an impossible path is not removed for linearity; a protocol loop of
  no iteration is nothing; static arguments compared as values make a loop stepped; equality on
  a composite with an opaque component is refused; a collected name after no iteration has the
  type the body gives or is `[]`; names in specifications must resolve; an `if` expression is
  an expression of its roles; `1^n` determines no `n`; whether a body can stop is read on its text.
