## 1. Question and assigned depth

This holdout asks whether the frozen semantic model silently assumes field
algebra, or whether it can represent proof components over Galois rings with
zero divisors, extension-ring challenges, ring-linear codes, and
Brakedown-style commitments.

The algebraic answer is clear: the shared model does not need a field-only
repair. Exact rings, extensions, code laws, challenge sets, and polynomial
relations are module- and profile-owned. The source-specified interactive
commitment, Sumcheck, ZeroCheck, Libra, and HyperPlonk components are therefore
`ProfileOrModule` at the assigned depth.

The complete paper-named **noninteractive SNARK** is `Undetermined`. The paper
defines a noninteractive SNARK, but its concrete sections present interactive
public-coin protocols and do not specify a Fiat--Shamir or other
noninteractive transcript transformation. Supplying one from background
convention would invent source semantics.

This source incompleteness demonstrates no shared-model defect and selects no
identity rotation.

## 2. Source lock and evidence boundary

The primary source is Yuanju Wei, Xinxuan Zhang, and Yi Deng,
*Transparent SNARKs over Galois Rings*, IACR ePrint 2025/263, exact PDF
recorded in `source-ledger.json`.

The source specifies:

- Galois-ring definitions, ideals, units, zero divisors, exceptional sets, and
  a generalized polynomial-zero bound;
- randomized expander-code constructions over large and small Galois rings;
- block packing into extension Galois rings for small base rings;
- an interleaved/repetition variant of the code-detection argument;
- an interactive Brakedown-style multilinear polynomial commitment;
- extraction through repeated random-matrix selection;
- Sumcheck and ZeroCheck over selected Galois rings;
- Libra-style and HyperPlonk-style PIOP compositions; and
- asymptotic cost and error claims.

The source calls the final constructions transparent SNARKs and defines a
noninteractive `(Setup, Prove, Verify)` interface. However, no concrete
Fiat--Shamir transform, random-oracle experiment, transcript framing, challenge
derivation, retry/failure law, or alternate noninteractive compiler is given.
The explicit polynomial-commitment evaluation, Sumcheck, and ZeroCheck
schedules remain interactive.

The distinction between “no trusted SRS” and “no public parameters” is also
preserved. The commitment construction still has exact code, hash, domain, and
parameter choices whose generation and use require semantic treatment.

No mathematical claim in the paper is established by this record.

## 3. Source-native algebra

### 3.1 Galois-ring structure

The source works with finite commutative local rings `GR(p^s,r)`. Their unique
maximal ideal is generated by `p`; zero divisors occur in that ideal, and only
units can be inverted. Polynomial identity and code-distance arguments cannot
reuse field cancellation or “nonzero implies invertible.”

The source distinguishes:

- a sufficiently large ring whose residue-field-sized challenge space is
  large relative to the security parameter;
- a small base ring that is embedded into an extension `GR(p^s,kr)`;
- coefficients that remain in the base ring;
- challenges that may live in the extension ring; and
- mixed base/extension linear operations.

An exceptional set requires every pairwise difference to be a unit. Challenge
admissibility therefore depends on exact ring and parameter laws, not merely
on finite carrier size.

### 3.2 Ring-linear codes

Zero divisors change the probability that a random linear combination
vanishes. The paper stratifies elements by powers of the maximal ideal and
derives ring-specific distance bounds for randomized expander codes.

For a small ring, adjacent base-ring elements are treated as one element of an
extension ring under a fixed extension representation. The resulting encoder
is still linear over the base ring. Interleaving and block-wise distance support
repeated small-ring challenges without mixing the original coefficients.

The fact that a sampled code has the required distance with high probability
is an Analysis proposition about exact setup parameters. It is not implied by
the type `Codeword` or by successful encoder evaluation.

### 3.3 Polynomial commitment

The commitment arranges the multilinear evaluation table as a matrix, encodes
its rows, and commits to the encoded matrix using a Merkle tree. During the
testing phase:

1. the verifier samples a random matrix over the selected base ring;
2. the prover sends claimed linear combinations;
3. the verifier samples a query set;
4. the prover opens the queried encoded columns with Merkle paths; and
5. the verifier checks authentication, encoding, and linear-combination
   equations.

The evaluation phase uses tensor-product evaluation vectors and a similar
linear-combination/opening procedure. The source's extraction argument samples
matrices until it obtains an invertible one; over a Galois ring, nonzero
determinant is insufficient unless the determinant is a unit.

### 3.4 Ring Sumcheck and ZeroCheck

The Sumcheck schedule is the usual public-coin recurrence, but its challenges
are sampled from an exact Galois ring or eligible exceptional set. Its
soundness expression depends on the residue-field size, degrees, and number of
rounds.

ZeroCheck first samples a ring vector and then invokes Sumcheck on an
equality-polynomial-weighted claim. Again, the ring-specific challenge and
zero-divisor premises are part of the theorem.

### 3.5 Libra and HyperPlonk variants

The Libra route is selected for log-space-uniform circuits because it avoids a
set-consistency subprotocol that is unsound under naïve ring polynomial
encoding. The HyperPlonk route uses direct Sumcheck-style permutation
constraints rather than the field-oriented set-consistency route. The source
gives an explicit modulo-eight collision example showing why those routes must
remain distinct.

The source does not claim a generic automatic lifting of every field PIOP to a
Galois ring.

## 4. Frozen owner mapping

### 4.1 Foundation owns exact algebraic modules

Exact semantic modules can own:

- each `GR(p^s,r)` carrier and canonical equality;
- addition, multiplication, additive inverse, unit testing, and partial
  inversion with exact failure;
- ideal/valuation classification and residue mapping;
- extension-ring construction and base-to-extension embedding;
- canonical block packing and unpacking under a fixed basis;
- exceptional-set membership;
- polynomial, matrix, tensor, codeword, and Merkle-value carriers;
- ring-linear encoders and mixed-ring algorithms; and
- exact code, hash, and evaluation algorithms.

The shared schema treats module-owned values as opaque. It therefore makes no
field cancellation, division, root bound, or invertibility assumption. This is
the intended extension mechanism.

For a fixed extension basis, block packing may form an exact equivalence
between a length-`k` base-ring vector and one extension-ring element, while the
base-ring inclusion forms an embedding. Neither law is inferred from the words
“extension ring”; it requires its own admitted bridge and law basis.

### 4.2 Interactive Core owns the source schedules

The commitment test/evaluation, Sumcheck, and ZeroCheck schedules use ordinary
typed effects:

- public setup and statement inputs;
- prover Messages for matrices, polynomials, evaluations, and Merkle evidence;
- FreshChallenge values for random matrices, ring elements/vectors, and query
  sets;
- logical Oracle queries and answers where the source is expressed as a PIOP;
- commitment/opening checks, recurrence checks, degree checks, and final
  identities; and
- exact accept/reject/failure terminals.

One random matrix or query set may be one structured Challenge value with an
exact joint distribution. Treating its entries as independent calls is valid
only when the exact source distribution proves that factorization and preserves
sampling without replacement where required.

The challenge `ValueType` is the selected ring or extension ring. Core does not
need to know whether an element is a unit; the exact sampling contract and
profile-local checks own that condition.

### 4.3 Plan owns honest code, commitment, and proof construction

The Plan owns matrix layout, block packing, row encoding, Merkle construction,
linear combinations, ring-polynomial messages, quotient/evaluation data, and
opening evidence. Every recipe reads only earlier messages and challenges.

Randomized code generation or setup is not silently moved into an honest
per-proof Plan if it is fixed public parameter material. Its source occurrence,
distribution, and trust/provenance route must be selected separately.

### 4.4 Relations owns ring circuits and exact correspondence

Exact Relations profiles can express:

- arithmetic-circuit satisfaction over a selected Galois ring;
- multilinear evaluation-table correspondence;
- base/extension embedding and mixed-operation equations;
- code membership and distance predicates;
- commitment-opening and Merkle authentication equations;
- Sumcheck and ZeroCheck claim transforms;
- Libra layer relations;
- HyperPlonk gate and direct permutation relations; and
- failure of the field-style set-consistency encoding over rings with zero
  divisors.

Probabilistic code distance, challenge soundness, Merkle binding, extraction,
and succinctness do not become Relations truth. They remain Analysis
propositions and losses.

### 4.5 Checked Oracle commitment is available but profile-local

The logical PIOP Oracles and the Merkle-committed target remain separate
Protocols. The checked Oracle-commitment construction can describe the exact
source/target map, setup roles, commitments, query/opening evidence, and
verifier algorithms for one Brakedown profile.

Structural admission establishes no collision resistance, code distance,
binding, extractability, or argument security. Those assumptions and theorem
applications belong to Analysis.

### 4.6 Analysis owns all probabilistic and theorem claims

Source-pinned Analysis profiles would be required for at least:

- randomized code-distance formation under exact ring parameters;
- the repetition/block-distance detection claim;
- commitment completeness and binding;
- extraction via random invertible matrices;
- ring Sumcheck and ZeroCheck soundness with exact error expressions;
- Libra and HyperPlonk protocol applicability;
- Merkle collision resistance;
- PIOP-to-interactive-argument correspondence;
- any Fiat--Shamir/random-oracle compiler;
- knowledge soundness, succinctness, and transparency; and
- the asymptotic cost claims.

The parameterized phrase “arbitrary Galois rings” denotes a family with an
extension construction and explicit prerequisites. It is not one universal
finite Core or one theorem-free module.

## 5. First failed and tempting mappings

### 5.1 Reuse a field profile by changing the carrier name

**Attempt.** Instantiate ordinary field polynomial and code laws with a Galois-
ring value type.

**Failure.** Nonzero elements need not be units; cancellation, root, matrix-
invertibility, distance, and set-consistency arguments change.

**Disposition.** Exact ring modules and relation/theorem profiles. Shared Core
remains algebra-opaque.

### 5.2 Treat base and extension rings as the same exact type

**Attempt.** Allow base coefficients and extension challenges to substitute
because the base ring embeds in the extension.

**Failure.** They have different exact `ValueType`s and operations. Block
packing and scalar inclusion are different maps, and mixed multiplication has
an exact ABI.

**Disposition.** Profile-local embedding/equivalence bridges plus explicit
mixed-ring algorithms.

### 5.3 Infer code distance from a successful encoder call

**Attempt.** Regard `Encode(input) = codeword` as proof that the sampled code
has the paper's relative distance.

**Failure.** The code construction's distance statement is probabilistic and
parameter-dependent. Encoder totality does not prove it.

**Disposition.** Relations owns exact encoding; Analysis owns distance and
setup applicability.

### 5.4 Reuse field set consistency in HyperPlonk

**Attempt.** Import the field-oriented product-polynomial set check unchanged.

**Failure.** Different sets can produce equal polynomials in rings with zero
divisors; the source gives an explicit counterexample modulo eight.

**Disposition.** Use the source's direct Sumcheck permutation relation and
retain the counterexample as a negative control.

### 5.5 Call the interactive construction a noninteractive SNARK

**Attempt.** Package the prover/verifier messages as one proof while omitting
how verifier challenges are derived.

**Failure.** The concrete source schedules are interactive. Proof packaging
does not create random challenges or establish transcript binding. The paper
does not specify a Fiat--Shamir or other noninteractive compiler.

**Disposition.** `Undetermined` for the complete source-named SNARK. A future
design may select an independently specified checked transcript construction,
but it cannot claim literal source correspondence for an omitted transform.

### 5.6 Treat transparency as absence of setup

**Attempt.** Remove code, hash, domain, and public-parameter material because
the scheme has no trusted SRS.

**Failure.** Transparent setup still has exact algorithms and public
parameters. Their generation, distribution, and admissibility affect the
protocol and theorem.

**Disposition.** Explicit public-setup profile with no trusted-SRS claim only
after exact Analysis support.

## 8. Classification and nonclaims

The required single primary classification is **`Undetermined`** for the
complete source-named noninteractive SNARK. The source does not close the
challenge-generation/transcript path needed to reconstruct that subject.

The strongest subordinate result is **`ProfileOrModule`** for every explicit
interactive component and for the assigned ring-versus-field pressure. No
shared semantic profile rotates: the frozen model contains no universal field
law that the ring construction contradicts.

This analysis does **not** establish:

- an executable Galois-ring fixture;
- any concrete ring, code, extension, hash, Merkle, challenge, or parameter
  profile;
- correctness of the paper's algebra or proofs;
- code distance, binding, extractability, soundness, knowledge soundness,
  succinctness, or transparency;
- zero knowledge, which is not established by the selected source record;
- a noninteractive protocol or Fiat--Shamir security;
- practical support for the paper's parameter sizes; or
- equivalence to an implementation.
