## 1. Question and answer

D1 established that five exact admitted Cores support one integrated static
`PublicCoinView`. D2 asks the separate schema question: can each admitted Core
and Fresh Protocol determine one finite completed-record body that fixes every
occurrence receipt, all three Fresh Challenge receipts, all Oracle receipt
branches and visibility/type laws, terminal completion, stopped partial
prefixes, and provider-facing outcome lanes?

The answer is affirmative for five exact candidate bodies in the selected B2B
description universe. A typed owner projector and an independently compiled,
cold byte-derived projector agree on every body and canonical byte. The package
derives these schemas from admitted Core and Fresh Protocol sources only. It
does not execute a run and does not claim replay.

This is a representability result over explicit candidate choices. It is not a
claim that the current target text already determines those choices. Five
owner-text gaps remain `CannotAnswer` and must be selected before F0-V2C.

## 2. Exact candidate boundary

For each D1 carrier, the candidate `ExecutionView` fixes:

- 23 occurrence receipt entries with occurrence coordinates, output arities,
  and output value types;
- three Fresh Challenge receipt entries with Challenge and occurrence
  coordinates, the Fresh law, and value type;
- nine Oracle receipt entries: Published, Queried, and Answered for each of
  FullCanonical, PublicBinding, and LogicalAccess;
- publication visibility and exact published, queried, and answered value
  types, including a typed zero-output fixation marker for LogicalAccess;
- three completed terminal alternatives with terminal reference, occurrence,
  verdict, exact active receipt prefix, and public-output types;
- `CompletedRun | InterpretationFailed | StrategyStopped`, where Fresh fixes
  `InterpretationFailed` to `None` and each stopped alternative carries the
  terminal-delimited partial prefix; and
- the eight qualified operational noncompletion cases outside that record
  sum.

Each case is bound to a separately named schema definition. The external
partition is `Unsupported`, `MissingDependency`,
`CannotAnswer`, `KindMismatch`, `Malformed`, `Refused`,
`DeterministicLimitExceeded`, and `CheckerFailure`. This supplies the
provider-facing lanes requested by the F2-O0 handoff without turning outcomes
into authored run records or introducing a new owner.

## 3. Evidence construction

The D2 schema is a source delta over the exact B5B2/D1 schema source. Both B2B
compilers reconstruct the same 101-definition, 503-node finite grammar before
any carrier is projected.

The typed path reuses D1 admission to authenticate exact Core, Fresh Protocol,
profile, module, algorithm, and evaluation-contract closure. It projects the
completed-record candidate from the admitted static authority.

The cold path imports no typed D2 model. It independently compiles the schema
delta, authenticates raw Core and Protocol bodies and references, parses the
relevant Core tables, and reconstructs the same schema. Agreement is over five
distinct values and five canonical bodies totaling 168,652 bytes, not over a
single Boolean. All bodies round-trip and typed reprojection is deterministic.

The construction does not call a runtime strategy, sample a Challenge, produce
receipt values, execute a run, or execute a replay. The executable metrics pin
both run and replay counts to zero.

## 4. Mutation boundary

Ten structurally encodable substitutions isolate the exact owner claim. The
gate refuses a changed receipt branch, coordinate, visibility, arity, or value
type; a changed terminal reference or stopping terminal; an added receipt for
an inactive post-terminal occurrence; an omitted LogicalAccess fixation
marker; and a PublicBinding-to-FullCanonical upgrade.

Each mutation has its own stable refusal code. This matters because a common
schema can describe both the candidate and a neighboring body; successful
encoding alone cannot confer owner truth. Cold controls separately classify
truncation as malformed and refuse cross-Core Fresh substitution and an
incomplete algorithm closure.

## 5. Target obligations exposed by D2

The experiment returns `CannotAnswer` for five exact owner decisions.

### 5.1 LogicalAccess fixation placement

`docs-next/pir/interactive-core.md:1091-1092` requires a typed public fixation
marker for zero-output LogicalAccess publication. The `Published` receipt at
lines 1758-1765 carries only `outputs`, so the target does not say where that
marker lives in the record schema. D2 places it in the publication observation
for the candidate only.

### 5.2 Terminal receipt prefix

Line 1704 stops generation after the first active terminal, while lines
1767-1775 give `RunRecord.occurrence_receipts` no exact terminal-inclusion and
prefix rule. D2 includes receipts through the active terminal for the
candidate. The owner text must select this explicitly.

### 5.3 Partial-run body

Line 1777 describes `PartialRunRecord` as an exact prefix but does not define
its fields, terminal/stopping coordinate, or canonical body. D2 freezes one
terminal-delimited body only as a candidate.

### 5.4 Record-sum ownership

Lines 1791-1794 define `CompletedProtocolRecord` without `StrategyStopped`, and
lines 1814-1817 say a partial record is diagnostic data rather than a completed
record. The F2-O0 handoff asks D2 to carry provider-facing outcome lanes. D2
therefore demonstrates that a three-lane schema is finitely expressible but
does not claim that PIR has selected it or that `StrategyStopped` is a
completed protocol record.

### 5.5 ExecutionView field name

The `ExecutionView` display at line 2128 says `run_record_schema`; the census
candidate says `completed_record_schema`. An owner publication must select one
field name and regenerate the dependent identity cone.

These are PIR owner-text changes, not grounds for a transcript-root authority,
semantic MLIR token, or separate runtime-schema owner.
