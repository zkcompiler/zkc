## 2. Why B2 must be split

The earlier B2 entry contract called for constructor-isolation pressure plus an
integrated carrier. That direction is retained, but one B2 gate would conflate
four different questions:

1. can the complete owner schema describe every constructor;
2. can every schema branch be inhabited by a typed boundary value;
3. can an offline evaluator admit a subject using that constructor; and
4. do the owner derivation and `PCGraph` laws remain correct when constructors
   interact?

An integrated fixture can pass while one schema branch is unreachable. A
schema inhabitance test can pass while owner admission would refuse the same
carrier. A graph can have the expected final Boolean despite two compensating
edge errors. B2 therefore becomes an internal four-stage program:

```text
B2A  source census, exact B1 delta, pressure topology      [complete]
  -> B2B  complete schema source and constructor inhabitance [complete]
  -> B2C  isolated admitted carriers and owner projections  [open]
  -> B2D  integrated carrier and full PCGraph pressure       [open]
```

This does not add a roadmap phase or owner. It is the falsification topology
inside the already selected F0-V2B2 research gate.

## 5. Pressure topology

### 5.1 Values, scopes, and messages

Isolation carriers must distinguish an unused Verifier-private input from a
private dependency reaching a sink. Constants and total derived values must
exercise exact algorithm ABI, predecessor, and topological-order checks. A
child scope with an explicit opening and nontrivial guard must pressure scope
paths, opening order, and `GuardImplies`. A deterministic Verifier message
must pressure ordered inputs and the deterministic-public transfer rather than
being treated as a Prover publication.

### 5.2 Oracle product, not representative samples

The minimum complete Oracle pressure is the cross-product:

```text
origin       InitialOracle | ProverOracle
mode         FullCanonicalOracle | PublicBinding | LogicalAccess
visibility   Public | VerifierOnly for Query/Answer
```

The six origin/mode carriers are separate because origin changes decision
ownership, while mode changes publication outputs, replay witness needs, and
the logical-access representation obligation. Both query visibilities are
separate because only Public queries may enter Prover-visible history, while a
Verifier-only dependency reaching a public sink must classify private.

The logical-access carrier must preserve the zero-output fixation marker and
retain its complete influence cone and acceptance intersection. A transcript
containing all observed queries and answers does not bind unqueried entries and
cannot substitute for this graph check.

### 5.3 Claims, reductions, and correlation

The isolation set includes both initial-binding and reduction-output claim
creation, Linear and Reusable usage, Consume and Discharge coordinates, and a
reduction with both before- and after-challenge publication requirements. The
negative discriminator checks the least `next_challenge`, publication kind,
scope/guard order, consumer coordinates, and Last-Challenge closure.

Joint challenge pressure requires dense group indices and exact prior-member
closure. Shared pressure requires at least two exact reduction-role consumers
and equality with the complete derived `ReductionConsumers` sequence. Equal
challenge values, equal domains, or ordinary dataflow uses do not create a
reduction consumer.

### 5.4 Module effects

One representative module effect is insufficient. B2C needs all three exact
decision classes:

```text
NoProverDecision
ProverDecision
ProverPublication
```

The view may keep the admitted module effect payload as one opaque canonical
atom, but admission and graph formation may not keep its law opaque. They must
authenticate the exact owner declaration and apply its payload schema,
ordered input/control/output edges, visibility, reconstruction ABI, sink
declarations, and public observation rule. A module-supplied Boolean such as
`publicly_recomputable` is not an admissible shortcut.

### 5.5 Terminals and Fresh runtime descriptions

The terminal suite covers Accept, Reject, and Abort, public outputs, required
checks, and both claim dispositions, while retaining an unconditional final
fallback. The Fresh runtime description must then enumerate all occurrence
output arities and types, all three Oracle receipt forms, both query
visibilities, Fresh challenge receipts, terminal references, and public-output
types. It remains a runtime schema, not a transport encoding or identified
receipt subject.

joint/shared challenges, module effects, and all terminal behavior. It must

The graph gate requires positive and negative pressure for:

- all fourteen `PCNode` cases;

Two graph implementations should compare complete node, edge, topological,

F0-V2B2 closes only after B2B, B2C, and B2D are all affirmative at their exact

## 10. Main-design conclusions

No new top-level formal kernel or authority is justified. The target pipeline
remains:

```text
exact Interaction profile
  -> immutable admitted Core / Protocol handle
  -> ephemeral normalized owner fact index
  -> simultaneously derived owner views
  -> schema-guided coordinates and manifests
  -> qualified downstream judgment
```

B2A adds three implementation requirements to the B1 conclusion:

1. the complete schema source must be generative enough to drive boundary
   inhabitance and validators, not merely hashing;
2. the second owner path should begin from strict canonical-body decoding, not
   the first path's host carrier; and
3. constructor isolation and integrated graph pressure are both mandatory.

These requirements strengthen correspondence without making the generated
code or proof producer authoritative. The checked source, independent
validator, admitted owner handle, and exact proposition remain distinct.
