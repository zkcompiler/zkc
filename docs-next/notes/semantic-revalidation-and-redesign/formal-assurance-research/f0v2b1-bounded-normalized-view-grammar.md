## 1. Outcome

The normalized B0 body family is executable over the exact admitted F1-R1B
finite Schnorr slice without adding a new semantic owner, portable view
subject, transcript authority, token algebra, or Foundation-wide kernel.

One finite candidate schema source compiles into six closed schemas. Five
values are derived from one exact admitted Core handle and the sixth from its
paired admitted Fresh Protocol handle. A recursive source compiler and an
independent worklist compiler agree. An algorithmic owner derivation and a
separately written finite fixture oracle also agree on the complete package:

```text
six schemas
six owner-derived values
six complete active-leaf manifests
329 active atomic leaves
```

The 63-case frozen gate has:

```text
12  Affirmative bounded findings
 5  CannotAnswer obligations
46  Refused mutations
```

This closes F0-V2B1 only. B1 uses maximum-zero sequences for every unexercised
constructor family, so its schema identities are deliberately not target
profile candidates. F0-V2B2 must replace those bounded holes with the complete
grammar and exercise every admitted constructor before F0-V2C may publish and
migrate the target.

## 2. What was tested

The gate consumes no caller-authored view fields. Each path separately:

1. loads the exact F1-R1B owner model;
2. constructs and admits its fourteen-field `InteractiveCore`;
3. forms and admits the paired Fresh `Protocol` from the live Core handle;
4. compiles the same finite normalized schema source;
5. derives all six view values from the admitted handles;
6. enumerates every active atomic coordinate;
7. requires the requested manifest to equal the complete sorted-unique leaf
   set; and
8. freezes schema, value, manifest, owner, and graph evidence.

The reference path uses recursive schema expansion, recursive leaf traversal,
general scope/backlink construction, and algorithmic `PCGraph` formation. The
second path uses a worklist compiler, breadth-first traversal followed by
canonical coordinate ordering, and an explicit finite oracle for the exact
fixture. The two paths do not share view-derivation code.

They do share the exact owner's primitive canonical body compilers for
`ValueType`, `ValueRef`, `Guard`, declaration references, and typed IDs. The
result is therefore diversity for schema expansion, owner projection, graph
formation, and manifest enumeration. It is not a second K1 encoder, an
independent Core admission evaluator, or a proof of those primitive body
compilers.

## 3. Candidate source shape

The source file is a finite macro language whose references compile away.
After expansion, the only semantic schema nodes are exactly the F0-V2A
universe:

```text
Record
Variant
Sequence
Atom(Unit | Natural | MetaBoolean |
     CanonicalBody(exact compiler) | ExactProfileLaw(exact law))
```

Named definitions are source-level body-compiler macros, not runtime schema
nodes. Both compilers reject cycles, unknown definitions, unused definitions,
unknown body compilers, unknown laws, non-strict ordinals, malformed source
nodes, and out-of-bound sequences. The fully expanded schema, not a macro name,
is committed in each candidate catalog entry.

The bounded source uses exact owner body compilers for IDs, declaration
references, Core-local refs, values, types, algorithms, contracts, and guards.
The only supported effect and read constructors are those actually present in
the admitted fixture. Unexercised family tables are not unconstrained lists:

```text
Empty := Sequence(max = 0, element = Unit)
```

This makes insertion structurally refusing while keeping the nonclaim visible.
It is a bounded test technique, not the F0-V2B2 target representation.

## 4. Six bounded derivations

### 4.1 Public binding

The one root scope forms with path `[ScopeRef(0)]`; the path is not an empty
host convention. The one Statement binding retains:

```text
BindingRef(0)
ScopeRef(0)
Statement
PublicInputRef(0)
exact Z/3Z ValueType
```

There is no `value_origin` field and no second producer-coordinate alias.
`ValueRef` is the exact producer coordinate, as selected in B0.

### 4.2 Strategy decisions

The Prover message occurrences at ordinals `0` and `2` are the two decision
refs. Each row retains its equal occurrence ref, complete root scope path,
complete `Guard`, message `ValueType`, and prior decision sequence.

The bounded guaranteed-read map has seven entries:

```text
decision 0:
  PublicInvocationInput(0)
  OpenedBinding(0)

decision 2:
  PublicInvocationInput(0)
  OpenedBinding(0)
  ObservedMessage(0)
  ObservedChallenge(1)
  PriorOwnMove(0)
```

Every entry carries the owner-derived `Z/3Z` type. This demonstrates why an
SSA-style value identity or one transcript token is insufficient as the view
contract: equal types and related values occur at distinct structural read
coordinates with different visibility meanings.

### 4.3 Public coin

The bounded graph retains all of the B0-selected evidence:

```text
nodes                    21
edges                    27
topological entries      21
StaticPublic classes      7
PublicHistory classes    14
VerifierPrivate classes   0
Invalid classes            0
sinks                      9
acceptance sinks           2
eligibility             true
```

The node set contains the public input, root opening, binding observation, six
activities, six effects, four occurrence outputs, and two terminal decisions.
The independently reproduced dependency edges include:

- scope and value dependencies of the binding;
- scope dependencies of every activity;
- the Check-output dependency of the guarded Accept activity;
- the first-terminal preemption dependency of the fallback Reject activity;
- activity-to-effect and effect-to-output edges;
- all four Check operands;
- the accepting Terminal's required Check; and
- both effect-to-terminal-decision edges.

The exact bounded Kahn order and every final class are retained in the view,
not recomputed by a consumer from an eligibility Boolean. The sink set includes
the six activities, invoked Check effect, and two Terminal decisions; the
bounded acceptance set contains the Check and accepting Terminal.

This is the first executable evidence that the B0 correction is useful rather
than merely more verbose. Omitting, reversing, or reordering an edge; changing
a class; dropping either sink kind; or flipping eligibility is refused by both
owner derivations.

The result remains bounded. No Verifier-private, Oracle, Reduction, or module
node exists, and neither `VerifierPrivate` nor `Invalid` transfer is exercised.
The general sink and transfer result is therefore `CannotAnswer`, not inferred
from the positive graph.

### 4.4 Effects and values

The view retains all six occurrence rows and their complete scope paths,
guards, structural effect constructors, and output types:

```text
0  ProverMessage(commitment channel, Z/3Z)  -> Z/3Z
1  Challenge(0)                             -> Z/3Z
2  ProverMessage(response channel, Z/3Z)    -> Z/3Z
3  Check(0)                                 -> Bool
4  Terminal(Accept)                         -> no outputs
5  Terminal(Reject)                         -> no outputs
```

The value table contains the public input and four occurrence outputs. The
Check output has the ordered four-value predecessor list; supplied Prover
messages and the independent Challenge have no direct value predecessor in
this fixture. Separate Message, Check, and Terminal tables retain their exact
declarations and occurrence backlinks. Their interiors remain structural
because current consumers select those fields.

### 4.5 Claims and reductions

The exact F1-R1B subject has no Claim, Reduction, or disposition. B1 therefore
forms only the Core ID plus three maximum-zero sequences. This proves that the
empty bounded case is unambiguous and rejects phantom rows. It says nothing
about the selected B0 creation/use/publication coordinate grammar.

### 4.6 Fresh execution

The view is bound to the exact admitted `ProtocolId` and its exact `CoreId`.
It retains one Fresh resolver coordinate for Challenge `0`, including the
occurrence, type, domain, fresh law, public conditions, and prior joint
members.

The completed-record description is structural. It lists output arity and
type for all six occurrence positions, one Challenge receipt description, no
Oracle receipts, and two Terminal record descriptions. It is not a transport
encoding, completed run, execution receipt, or content-addressed subject.
Changing an output arity or type is refused independently of a runtime value.

## 5. Mutation coverage

The forty-six refusals cover five boundaries.

| Boundary | Refused pressure |
|---|---|
| Source and schema | source digest, expanded field, catalog digest, missing/duplicate/cross-view manifest coordinate |
| Owner identity and binding | Core ID, Protocol ID, scope path, binding scope/type, retained Core mutation, Protocol/Core bearer substitution |
| Strategy and public coin | decision occurrence/guard/prior set, read omission/phantom/type, move type, graph edge/direction/order/class/sinks/eligibility, Challenge backlink/domain |
| Effect and value | occurrence guard/output type, value predecessor, Message backlink, Check algorithm/input order, Terminal verdict/backlink, phantom Claim |
| Execution and boundedness | resolver occurrence/domain, runtime arity/type, fixed execution/issuance laws, Oracle or extension insertion |

A mutation may still be structurally well-typed. It is refused because the
candidate value must equal the result independently derived from the retained
owner handle. Schema conformance and owner correspondence are separate checks.

## 6. Main-design conclusions

### 6.1 Keep the existing owner lifecycle

No new authority is needed. The useful pipeline is still:

```text
exact profile
  -> admitted Core / admitted Protocol handle
  -> ephemeral normalized owner fact index
  -> six simultaneously derived view values
  -> schema-guided coordinates and complete manifest
  -> existing source binding and capability lifecycle
```

The fact index remains unidentifiable and nonserializable. It exists to prevent
five independent reimplementations of scope, backlink, visibility, and graph
facts. It does not become `FSKernel`, a source root, or an Analysis authority.

### 6.2 Make retained owner state intrinsically immutable

The research `AdmittedCore` bearer is process-local but its Python slots can be
mutated after admission. B1 deliberately changes the retained body while
keeping the old bearer and shows that view formation must refuse by
recomputing the exact Core ID. It also substitutes another live Core handle
inside a Protocol bearer and refuses the mismatched pair.

The target contract should be stronger than relying on repeated defensive
rehashing alone:

```text
admission-owned immutable retained subject
+ unforgeable process-local issuer
+ exact subject/ID invariant at every authority-consuming boundary
+ exact Protocol/Core bearer pairing
```

Rechecking remains useful as defense in depth, but a mutable admitted bearer
must not be the intended implementation representation.

### 6.3 Publish a source contract, not host dataclasses

One finite data source compiled by two implementations is materially stronger
than two handwritten schema tables. The target should publish exact body
compiler source and dependency closure in the Interaction profile. Host
dataclasses may implement it, but their field names, reflection behavior, and
serialization cannot define the schema.

### 6.4 Do not promote the bounded identities

Maximum-zero families make B1 honest and mutation-friendly, but they would
incorrectly narrow target PIR. F0-V2B2 must form new complete schema bodies.
Those bodies will have different identities. F0-V2C must publish only the B2
result; it must not reinterpret or relabel B1 bytes.

## 7. F0-V2B2 constructor matrix

B2 must replace every bounded hole and force both derivations through at least
the following pressure:

| Family | Minimum affirmative carrier | Required discriminator |
|---|---|---|
| Values | Verifier-private input, constant, derived value | private path to sink becomes private or rejecting; derived predecessor omission refuses |
| Scopes and guards | child scope with explicit opening and nontrivial guard | wrong parent path, opening boundary, or implication refuses |
| Verifier message | deterministic public Verifier output | ABI/input omission or nondeterministic public output refuses |
| Oracles | Initial and Prover origin; Public and Verifier-only queries; WholeCarrier and LogicalAccess | missing publication/query/answer backlink, leaked private answer, or acceptance-relevant logical cone refuses |
| Claims | initial-binding and reduction-output creation | missing consumer, duplicate linear use, or terminal disposition mismatch refuses |
| Reductions | side inputs, challenges, before/after publication requirements, output contracts | reordered input/publication requirement or incomplete backlink refuses |
| Correlation | joint group and shared-reduction use | prior-member, group, index, or consumer-set mutation refuses |
| Module effects | no-decision, ProverDecision, and ProverPublication classes with control/output edges | payload reflection, undeclared edge, wrong owner, or unsupported declaration refuses |
| Terminals | Consume and Discharge dispositions plus public outputs | wrong disposition coordinate or public-output type refuses |
| PCGraph | `VerifierPrivate`, `Invalid`, logical influence, module control/output, terminal preemption | asserted eligibility without exact graph evidence refuses |

One giant fixture is insufficient because a compensating error can hide inside
an integrated graph. B2 should use one constructor-isolation suite plus at
least one integrated cross-family subject. Every affirmative carrier must be
admitted by an explicitly extended offline evaluator, while its report states
that the carrier is research support rather than current implementation
support.

The subsequent
[`F0-V2B2A census`](f0v2b2a-constructor-closure-census.md) authenticates 79
closed source/derived cases, measures twenty absent B1 variant cases and eight
maximum-zero references, and expands this matrix into twenty-three exact
pressure families. It refines execution into B2B schema/inhabitance, B2C
isolated admission/projection, and B2D integrated graph closure. This is a work
decomposition result, not constructor closure.

## 8. F0-V2B2 exit gate

F0-V2B2 may close only when:

1. the candidate source has no maximum-zero placeholder for a target-supported
   family;
2. every schema definition is reachable and every body compiler/law dependency
   is exact;
3. both source compilers derive identical six schemas;
4. two owner derivations agree for every isolation and integrated carrier;
5. all active coordinates resolve and every complete manifest is exact;
6. every `PCNode`, transfer class, sink rule, logical-access cone, and module
   boundary is positively and negatively exercised;
7. retained subject mutation and bearer substitution remain refusing;
8. old B1 identities are explicit negative controls; and
9. remaining uncertainty is target publication/migration or later read
   closure, not body grammar or constructor derivation.

Only then may F0-V2C update Interaction source, advance its local revision,
rotate the measured profile cone, and resume F1-R1C over published owner views.

## 9. Decision

Retain the B0 normalized view family and the F0-V2A finite schema algebra.
Adopt one PIR-owned finite schema source, two compiler implementations, one
shared ephemeral Core fact index, simultaneous five-Core-view derivation, and
separate Protocol-owned Execution derivation. Add an explicit immutable-owner
state requirement to the target implementation contract.

Proceed through F0-V2B2A--D. The B2B complete-schema and inhabitance gate now
passes at bounded structural resolution; proceed to B2C owner admission and
projection. Do not publish, migrate, form Q1, or resume the ArkLib/VCVio
provider lane from the B1 or B2B result.

## 10. Non-claims

B1 does not establish complete target grammar, constructor completeness,
general `PCGraph` correctness, current compiler correspondence, target source
publication, profile migration, source-capability issuance, proper-subset read
closure, Q1, theorem applicability, theorem truth, backend preservation, or a
cryptographic property. Its two derivations are finite executable evidence,
not a proof of the owner semantics or their implementation.
