# F0 Equal-Resolution Candidate Matrix

> **Kind:** Temporary generative/evaluative candidate comparison
> **State:** First equal-resolution pass complete; provisional convergence
> survived the paper scenarios, with machine F1 falsifiers still open
> **Authority:** None. The convergence result authorizes F1 research only; it
> does not change the selected target, public vocabulary, or implementation.

## 1. Evaluation frame

Each candidate is instantiated against the same required chain:

```text
admitted source
  -> independently inspectable source closure
  -> formal-provider subject
  -> checked correspondence
  -> theorem truth and applicability
  -> qualified Analysis property
  -> property-specific transition or realization use
```

The comparison gives no credit for hiding an edge. For example, making a Lean
term canonical does not eliminate the need to connect it to generated MLIR or
an endpoint; it moves that correspondence downstream.

The scoring vocabulary is:

- **strong** — the candidate has a natural exact owner and checker boundary;
- **conditional** — coherent only after a named contract, checker, or stable
  representation is supplied;
- **weak** — the architecture places the burden on convention, one trusted
  producer, or duplicated semantics; and
- **conflict** — the candidate contradicts a selected identity/authority goal
  unless that goal is deliberately reopened.

## 2. Candidate P — preserve with provider-local adapters

### Concrete shape

```text
live admitted owner handles and views
  -> provider-specific adapter invoked in the same process
  -> provider theorem result
  -> existing Analysis validation basis
```

There is no durable neutral package and no new identified reification subject.
Each provider adapter directly consumes the exact owner-issued views it needs.

### Identity, authority, and trust

- Protocol and all existing owner identities remain unchanged.
- Provider artifact and validation basis identify the external environment.
- The adapter is trusted unless its result is checked by an independently
  specified relation.
- Cross-process replay requires reconstructing all owner subjects and invoking
  the adapter again; there is no provider-neutral retained input.

### Strength

P is the smallest same-process prototype and a useful control. It can prove
that the current views are sufficient for one VCVio interpretation without
prematurely freezing a second representation.

### Failure

P is weak at the boundary F0 is meant to establish. An independently released
formal project should not need the C++/MLIR process, private capabilities, or a
provider-specific exporter merely to know the exact source observations. Two
adapters may silently select different source closures, and a durable proof
cannot be independently replayed from a stable neutral input.

P survives only as the F1 bootstrap mode or if the project explicitly decides
there will be no independent formal consumer, no retention promise, and no
separate release cycle. That would contradict the present research objective
and the target's documented formal-extraction trigger.

## 3. Candidate A — owner-derived formal interpretation views

### Concrete shape

```text
existing owner subject/view schemas
  -> Analysis FormalInterpretation source profile and exact manifests
  -> identified correspondence question
  -> provider-specific formal artifact
  -> checked Analysis result
```

Candidate A does not add a universal Protocol representation. It adds or
instantiates the minimum formal-interpretation family needed to select exact
owner reads and state a provider correspondence.

### Identity, authority, and trust

- Source authority remains with PIR, Interface, Plan, Relations, or another
  exact owner.
- Analysis owns the question, proposition, validation basis, checked result,
  and reliance capability.
- Provider syntax and theorem names do not enter Protocol identity.
- An exporter is replaceable and preferably untrusted.
- The checker binds every formal artifact to exact owner source coordinates.

### Strength

A matches the existing federated architecture. It reuses
`AnalysisSourceProfile`, `AnalysisSemanticReadManifest`, source support,
translation/checker contracts, and residual-trust closure rather than adding a
`FormalKernel`. Extension remains local: a new provider adds an adapter and
validation basis, not a Core variant.

### Failure

A alone does not decide persistence. If its views are only process-local, it
has P's independent-release weakness. If every provider invents its own
serialization, source closure ceases to be provider-neutral. A must therefore
be paired with S when the formal consumer is cross-process and independently
released.

## 4. Candidate S — stable neutral source package

### Concrete shape

```text
exact owner-issued views and manifests
  -> untrusted package exporter
  -> PortableSemanticReadPackage
  -> independent source-package checker
  -> provider-specific adapters
```

The package is a canonical source-authentication envelope plus a question-
relative source projection. It carries enough canonical owner preimage and
dependency material for independent root-ID recomputation, then exact source
coordinates, values, manifests, profiles, and an interpretation-contract ID.
It does not define a universal proof language.

### Identity, authority, and trust

- The package has a content identity distinct from every root owner subject.
- Its identity binds schema, source roots, manifests, entries, and contract.
- Independent decoders can recompute root IDs from packaged canonical
  preimages; they do not accept asserted IDs or depend on MLIR bytes.
- Package bytes and IDs are inert. A checked result plus fresh capability is
  required for zkc reliance.
- The exporter is outside the TCB.
- Independent decoders/checkers recompute canonical source IDs, closure, and
  package equality.
- Compatibility and retention are explicit package-schema policies rather
  than accidental MLIR compatibility.

### Strength

S meets the target's named trigger: a formal extraction boundary requiring a
complete stable neutral package. It permits VCVio, ArkLib, SSProve, EasyCrypt,
and future consumers to share one authenticated source closure while retaining
native provider languages. It also provides a stable falsifier corpus for
omission, aliasing, and replay bugs.

### Failure

An unconstrained S becomes a shadow Protocol. A single universal package that
copies Interface, Plan, Relations, experiments, and all future semantics would
freeze unresolved meaning and create a second owner. The repair is to make the
package **question-relative and manifest-complete**, with one exact source
contract and no provider semantics. New observations require a new contract
and package identity.

S also incurs real obligations: canonical schema, independent decoders,
compatibility policy, source-to-package checker, size/resource limits, and
cold-replay rules. These costs are justified only because the independent
consumer is explicit in F0's scenario. If the project declines that product
boundary, A plus a local P-style view invocation remains the smaller design.

Portable S excludes live confidential witness values, Oracle carriers,
mutable Plan state, and causal capabilities. Such inputs remain owner-local
support to a same-process checked proposition; role/type declarations may be
portable, but secret authority is not.

## 5. Candidate C — proof-carrying reification and transformation

### Concrete shape

```text
untrusted exporter or transformer
  -> candidate package/target + certificate
  -> receiver-owned checker
  -> checked correspondence or transition result
```

C is an evidence-production discipline, not a complete source architecture.
It needs A to define the proposition and normally S to define portable source
input.

### Identity, authority, and trust

- The certificate binds exact proposition, source/package or source/target
  IDs, checker/certificate-language version, and assumptions.
- Certificate bytes are derivation material, not semantic subject identity or
  authority.
- A false certificate is a validation-basis failure, not a negative Protocol
  or property result.
- A solver status without a checkable proof remains solver-trusted under an
  explicit basis.

### Strength

C removes complex exporters, proof search, and optimizers from the trusted
boundary. It composes naturally with zkc's unauthoritative proposal and
qualified-result architecture. Different producers can compete without
changing the source or proposition.

### Failure

Making a proof/certificate mandatory for ordinary Protocol admission would
couple base semantic availability to one assurance regime and make unsupported
providers a semantic failure. C should instead be mandatory only where a
policy requires a formal correspondence, property result, transition, domain
closure, or realization claim. Candidate C by itself cannot say what the
certificate proves.

## 6. Candidate R — formal semantic center

### Concrete shape

```text
proof-assistant/effect-calculus source subject
  -> formally defined Core/Protocol/Relations semantics
  -> verified or validated projection to carrier/MLIR
  -> verified/validated passes and endpoint lowering
```

The formal source becomes canonical. C++ and MLIR no longer define the primary
semantic subject; they decode or project from it.

### Identity, authority, and trust

- Canonical identity is formed over the formal source language or its neutral
  encoding.
- A proof kernel and formal source semantics enter the foundational TCB.
- Every current owner view, carrier decoder, pass, and endpoint needs a
  projection/refinement theorem or validation path.
- Provider neutrality requires either a neutral formal source independent of
  Lean/Rocq/EasyCrypt or a deliberate proof-assistant product commitment.

### Strength

R can make many source/formal correspondence obligations definitional and is
the clearest route to a CompCert-style verified stack. If zkc's primary product
becomes a formal protocol language whose executable compiler is secondary,
this may be the right long-term architecture.

### Failure

For the current product, R centralizes heterogeneous owner meanings in one
formal language and couples semantic evolution to a proof environment. It
weakens independent implementation, duplicates or replaces the already closed
profiled semantic identity, and creates the largest rotation cone precisely
while OIR/Realization remain unactivated. It still cannot avoid formal
correspondence to the MLIR carrier, cryptographic libraries, or deployed code.

R is rejected for the v0 formal bridge unless F1 demonstrates that exact owner
views cannot form a complete source package or that every viable provider
adapter necessarily redefines Core meaning. It remains a future product-level
reversal option, not an implementation optimization.

## 9. Provisional convergence

The first F0 convergence is:

```text
Candidate A  semantic and authority architecture
  + Candidate S  stable provider-neutral source package
  + Candidate C  default untrusted-production/checking discipline
  + Candidate P  disposable bootstrap implementation
  with Candidate R retained as a reversal comparator
```

More concretely:

1. existing semantic owners continue to define and admit source meaning;
2. Analysis gains or instantiates a formal-interpretation question/result
   family over exact owner source manifests;
3. when the independent-release scenario is selected, the formal-extraction
   boundary selects a stable neutral source-authentication envelope plus a
   question-relative source-read projection, with at least two independent
   decoders/checkers;
4. provider-native formal artifacts remain separate and use partial checked
   translation contracts;
5. exporters, proof search, and transforms are untrusted by default and may
   emit checkable certificates;
6. successful checks mint scoped qualified capabilities; inert records never
   carry authority; and
7. Compiler and Realization consume only property-specific checked results,
   never a generic “formally verified” bit.

This is an aggressive design, not a compatibility-only patch: it activates the
previously deferred formal-extraction trigger and adds a durable independent-
consumer boundary. It is conservative only about semantic authority: the new
package does not become a Protocol owner.

## 10. Required design changes if convergence survives

The durable target would need, at minimum:

- an explicit formal-interpretation Analysis family or an exact documented
  instantiation of the generic source/translation machinery;
- a stable package schema and identity preimage;
- owner-specific package read catalogs and exact closure laws;
- source-package and provider-correspondence question/result schemas;
- untrusted exporter and independent checker contracts;
- package compatibility, retention, resource, and cold-replay policy;
- provider environment and theorem-source-validation identities strong enough
  to distinguish revisions, dependency locks, axioms, and checker modes;
- exact negative/noncompletion outcomes; and
- one property-specific Compiler transition family for the first preservation
  pilot.

No change to `InteractiveCore`, Protocol identity, Relations ownership, or the
Compiler's validated-decision split is currently justified.

## 11. Reversal conditions

The A/S/C convergence is reopened if any of the following is demonstrated:

1. a theorem-relevant observation cannot be selected through a complete exact
   owner view without changing Core meaning;
2. question-relative packages cannot share a stable schema without becoming a
   universal shadow Protocol;
3. independent checking requires trusting the exporter because the source
   identity or required-read closure cannot be reconstructed;
4. provider-native semantics cannot be related through partial adapters
   without a shared universal formal calculus;
5. cold replay cannot bind exact source, package, provider environment, and
   proposition without serializing authority; or
6. a formal-source center yields a substantially smaller total trusted and
   migration boundary after carrier, compiler, and realization obligations are
   counted.

## 12. Non-claims

This matrix alone does not complete F0, select durable names, define package
bytes, prove checker soundness, or establish any theorem. Candidate scores are
architecture judgments backed by the current reconstruction and cited method
patterns; the scenario dossier and F1 prototype must still attempt to falsify
them.
