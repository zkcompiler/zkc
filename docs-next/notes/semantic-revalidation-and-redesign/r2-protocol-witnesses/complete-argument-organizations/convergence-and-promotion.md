# Complete-Argument Convergence and Promotion

> **Kind:** Temporary research-package closure record
> **State:** Complete at assigned T1/T2 depths
> **Authority:** None. The durable pages named below own promoted target laws.

## 1. Closure verdict

The package objective is achieved. Four materially different complete-
argument organizations do not require a universal Argument, ProofPackage,
lookup, polynomial-proof, accumulator, or runtime child-Core object.

The retained organization is:

```text
Relation meaning
  + one flat verifier-observable Core
  + one exact ChallengeInterpretation
  + Interface/OIR proof projection
  + one independently admitted ProverPlan
  + exact verifier profiles only where their shape applies
  + Relations correspondence
  + Analysis/Evidence premises and properties
```

The source cases close with one primary classification each:

| Case | Classification | Depth |
|---|---|---:|
| PLONK + Plookup | `ProfileOrModule` | T2 |
| Groth16/QAP | `Native` | T2 |
| Bulletproofs range + IPA | `Native` | T2 |
| LogUp-GKR + Logup* | `Native` | T1 |

The Groth16 classification uses the source-level public CRS control. A
minimal-verifier, setup-parametric Plan motivates a separate lifecycle
candidate but does not change the case's primary result.

## 2. Shared decisions retained

1. **A complete argument is an assembly, not a root.** Its participants have
   distinct identity and substitution laws.
2. **One verifier execution has one flat finite Core.** Claims and reductions
   preserve logical subargument boundaries without introducing child
   transcripts or verdict authorities.
3. **Proof bytes are Interface/OIR projection.** Physical aggregation cannot
   erase semantic message/challenge causality.
4. **Commitment verification is shape-directed.** PLONK uses an exact two-
   point KZG profile; Groth16 and the selected Bulletproofs encoding do not.
5. **Zero-challenge Cores are valid under Fresh.** No `Direct` tag is added.
6. **Canonical Fiat--Shamir requires a declared Challenge occurrence.** A
   zero-challenge transcript transforms no coin and adds only irrelevant
   work/failure surface; digesting belongs elsewhere. This exact-use law does
   not assert that every declared Challenge is dynamically reachable.
7. **Setup correspondence is not structural admission.** Relation binding,
   canonical keys, and successful verification do not prove setup origin,
   ceremony honesty, or theorem applicability.
8. **Finite unrolling does not imply family theorems.** Uniformity,
   asymptotics, and all-size security remain Analysis questions.

The nonempty-challenge law is not prose-only. It changes canonical-framed FS
admission semantics and therefore rotates `PIRCanonicalFramedFSProfileId` and
future exact importing profile IDs under the target's own identity law. It
does not alter any already challenged Core schedule or subject body.

Commitment-opening use admission now requires every claim, context, and
evidence coordinate to have an inclusive Section-11 dependency closure
classified only `StaticPublic` or `PublicHistory`. This rotates the commitment-
opening profile, every verifier-profile/use identity under it, and the
importing Oracle-commitment profile and profiled subjects. It leaves the
Interaction profile, Core, Protocol, Interface, and Plan identities unchanged.

## 4. Plan candidate routed forward

The package retains this preferred candidate:

```text
PublicProverParameterDecl = {
  key: PublicProverParameterKey,
  value_type: ValueType
}

RecipeOperand += PublicProverParameter(PublicProverParameterRef)
```

It would let a reusable Plan consume public proving-key or prover-side SRS
material without putting a prover-only projection into verifier identity or
automatic transcript absorption. The declaration would contain key and type,
not runtime value, supplier, setup result, relation, or provenance. It would
remain outside `ProverView`, `PlanWitnessSurface`, relation witness, and Core.

Promotion is deferred for a concrete reason, not uncertainty about its local
shape. Changing `ProverPlanBody` and `RecipeOperandBody` rotates the
Interface/Plan profile and affects dependent endpoint, OIR, and Relations
profiles. The immediately following folding/accumulation research has exposed
another possible Plan extension: deriving a private output witness after the
last verifier challenge without emitting a fake Core message. The two Plan
changes will be co-designed and, if retained, promoted in one dependency-
complete rotation.

The candidate is an ideal lifecycle improvement, not an expressibility
blocker. Source-level controls remain valid:

- Groth16 may expose the full formal public CRS as a Core parameter;
- a setup-specialized Plan may embed one fixed public value; and
- PLONK's source-selected common preprocessing remains Core-visible and
  transcript-bound.

## 5. Rejected changes

The package rejects:

- a first-class Argument or ProofPackage semantic ID;
- a universal setup-result or setup-ceremony root;
- a universal lookup or polynomial object;
- a generic commitment or batch flag;
- runtime child-Core composition for PLONK, IPA, or finite GKR;
- a new `Direct`/`Native` challenge interpretation;
- use of the commitment-opening profile for arbitrary mathematical
  commitments or pairing equations;
- treating helper proof advice as application relation witness; and
- automatic activation of soundness, knowledge, zero knowledge, setup trust,
  or Fiat--Shamir properties.

## 6. Evidence and validation boundary

The package carries pinned primary-source revisions and strict constructive T2
records for PLONK, Groth16, and Bulletproofs: each fixes one finite member,
typed owner and identity dependencies, a complete schedule/construction graph,
grounding obligations, a qualified failure partition, intrinsic bounds, and
negative mutations. The lookup variants retain a source-limited T1 boundary.
An adversarial architecture review corrected three initial overclaims:

1. the Plan public parameter lane is an architecture opportunity rather than a
   source-forced expressibility repair; and
2. zero-challenge canonical FS is not operationally identical to Fresh because
   it still performs transcript work. It is rejected because no Challenge is
   transformed, not because no work occurs; and
3. public commitment-opening evidence needed an explicit public-dependency-
   closure admission law rather than a prose-only replay claim.

No new evaluator was built. Static schedules and owner graphs distinguish the
candidate architectures without an execution-sensitive ambiguity. Existing
PLONK, LogUp, FRI, and commitment probes are retained only as bounded regression
anchors for the target laws they actually exercise.

## 7. Nonclaims

This package does not establish:

- implementation or wire-format support for any reviewed argument;
- completeness, soundness, knowledge, extraction, or zero knowledge;
- setup trust, key/relation correspondence, binding, or generator
  independence;
- exact ROM/QROM applicability or security of challenge sharing;
- correctness of protocol-specific source reconciliation;
- all-size expressibility, asymptotic resource laws, or performance; or
- semantic freeze, migration readiness, or Stage 4B activation.
