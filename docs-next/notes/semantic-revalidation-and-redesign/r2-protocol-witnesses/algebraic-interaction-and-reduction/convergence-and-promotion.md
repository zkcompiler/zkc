## 1. Result

The four cases do not justify replacing the verifier-observable
`InteractiveCore`, its structural claim/reduction graph, or the factorization
between one Core and multiple challenge interpretations. They instead produce
one asymmetric result:

1. explicit-polynomial classical Sumcheck is a native finite Core;
2. fixed-depth modern GKR is a native flat finite Core rather than a runtime
   hierarchy of child protocols;
3. packed Boolean GKR is the same interaction category with profile-local
   algebra and realization-local cost choices; and
4. the ideal-overwrite-duplex transform requires a conservative extension to
   the Fiat--Shamir construction envelope, not a change to the source Core.

The package therefore preserves the central architecture while narrowing one
overbroad support description. It does not implement the duplex extension or
activate any new Analysis family.

## 2. Final classifications

| Case | Classification | Exact reason |
|---|---|---|
| Classical Sumcheck with an explicit bounded polynomial | `Native` | Its messages, local checks, challenges, derived claims, reductions, rejection paths, and final evaluation form one finite typed interaction. |
| Fixed-depth modern Boolean-MLE GKR | `Native` | Output compression, every layer Sumcheck, line reduction, and the final input check can be authenticated as one flat occurrence and claim graph. |
| Packed Boolean GKR from the reviewed recent construction | `Native` | The existing typed algorithm/module and Relations dependencies express the high-degree first round, interpolation domain, Boolean identities, and degree bounds; packing and word-RAM optimizations are Plan or realization choices. |
| Ideal-overwrite-duplex Fiat--Shamir | `ConservativeExtension` | Its state-transition shape fits the Foundation algorithm/module substrate, but the active Fiat--Shamir envelope cannot express runtime-instance initialization, transform-owned proof salt, and its exact codec/squeeze discipline without changing the named construction. |

These classifications apply only to the reconstructed forms and assigned
constructive depth. They do not imply family-wide implementation support or
any security theorem.

## 3. Selected architecture

```text
relation-bound statement and residual claims
                    |
                    v
       one finite verifier-observable Core
       messages -> checks -> challenges -> reductions
                    |
          +---------+---------+
          |                   |
       Fresh              Fiat--Shamir
   interpretation        interpretation
                              |
                   one closed construction arm
                     /                    \
             strong-framed       ideal-overwrite-duplex
                 active          requested, not active
```

The Core records interaction and structural claim flow. Relations supplies the
mathematical meaning of statements, residual claims, reductions, wiring, and
final grounding. Analysis owns soundness, completeness, theorem
applicability, quantitative error, restoration conditions, and property
transport. Plan and realization own packing, caches, tables, vectorization,
and comparable operational choices.

No layer is permitted to infer the next layer's judgment merely because its
own structural check succeeded.

## 5. Deliberately not promoted

The following attractive shortcuts were rejected or deferred:

- no generic polynomial value or unbounded polynomial-evaluation Oracle in
  the common Core;
- no runtime child-Core call, universal transition algebra, or authenticated
  template handle in GKR execution;
- no reusable composition/elaboration satellite until another case makes its
  provenance operationally necessary;
- no authored absorb/skip flag and no global weakening of protected transcript
  influence;
- no treatment of transform salt as Core SessionContext or a source-Core
  prover message;
- no RAM-consistency semantics inferred from a word-RAM prover cost analysis;
- no polynomial-commitment scheme imported into the packed GKR interaction;
- no Sumcheck, GKR, state-restoration, duplex, or Fresh-to-duplex theorem
  profile; and
- no executable witness merely to restate a distinction already decided by
  the typed object graphs and source counterexamples.

## 6. Decisive positive and negative evidence

The selected model has complete positive encodings for the three representable
cases and a decisive typed obstruction for the fourth:

- a concrete two-round Sumcheck over `F_17`, including both rejecting paths
  and the final evaluation;
- a concrete one-layer GKR trace plus the parameterized graph from output
  compression through the public-input terminal check;
- an exact finite packed-GKR schedule including both the novel univariate and
  ordinary within-copy rounds; and
- an exact field-by-field obstruction comparison between the active strong-
  framed construction and the paper's duplex construction.

The decisive negatives are independent of implementation spelling:

- a challenge sampled before the message it must bind violates Core order and
  source causality;
- an opaque host wiring evaluator lacks an exact dependency owner;
- `AND(a,0)=0` does not establish that `a` is Boolean, so input Booleanity is
  an explicit relation premise;
- a word-RAM cost model supplies no address trace or memory-consistency
  semantics; and
- moving duplex salt into the source Core changes the Fresh interaction, while
  replacing raw source codecs with canonical frames describes a different
  Fiat--Shamir construction.

These counterexamples are sufficient to discriminate the compared candidates.
An executable discriminator would add repetition without deciding a remaining
architecture question.

## 7. Exact open work and order

The research package is complete at constructive depth, but the broader model
is not frozen. The resulting work is ordered by dependency:

1. specify and pressure a closed `IdealOverwriteDuplexV0` construction arm
   with runtime-instance initialization, transform-owned public construction
   material, exact codecs, exact state transitions, and distinct identity;
2. rerun the existing Fresh/Fiat--Shamir structural cases against the extended
   closed sum without weakening the strong-framed arm;
3. define a Sumcheck/GKR Analysis family only when theorem applicability and
   quantitative soundness become the next selected research question;
4. add checked reusable elaboration only if a later protocol requires retained
   template provenance rather than mere flat expressibility; and
5. continue to the Oracle and commitment cluster after the Fiat--Shamir
   construction boundary is either extended or explicitly retained as a v0
   limitation.

The first item is the only model-extension request produced here. The third
and fourth items are independent later work and must not be bundled into it.

## 8. Reversal conditions

Reopen the selected flat-Core conclusion if a source-faithful finite protocol
requires runtime-generated interaction that cannot be authenticated by a
bounded elaboration, or if two source-equivalent flat bodies require different
runtime meaning that Relations and Analysis cannot recover.

Reopen the native classification for packed GKR if a later construction uses
observable word-address state, memory consistency, or another effect that
changes verifier interaction rather than only prover cost.

Reopen the local Fiat--Shamir extension if source-exact construction material
cannot be scoped and authenticated without changing Core execution, or if two
materially different transforms require a shared law that a closed
construction sum cannot express.
