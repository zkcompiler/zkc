## 1. Central question

Can one finite, verifier-observable Protocol model represent classical
Sumcheck, layered GKR, a stateful duplex Fiat--Shamir interpretation, and a
recent GKR/RAM organization without confusing any of the following?

- temporal interaction with logical claim transformation;
- a structural reduction occurrence with a proof-theoretic reduction;
- child-protocol composition with a host callback;
- shared or reused challenges with accidental equality;
- transcript state with the Interactive Core state;
- relation meaning with Protocol execution;
- theorem applicability with constructive expressibility; or
- profile-local algebra and cost choices with kernel semantics.

The package may preserve, complete, locally extend, or redesign the candidate
model. Compatibility with the current implementation is evidence, not a
selection constraint.

## 2. Frozen case set and source classes

The design set contains four contrasting cases:

1. classical Sumcheck as the minimum multi-round algebraic reduction;
2. canonical layered GKR as nested Sumcheck with layer-to-layer claim
   evolution and verifier-held state;
3. the ideal-duplex Fiat--Shamir transform as a stateful challenge
   interpretation over an unchanged public-coin interaction; and
4. the recent Boolean-circuit/RAM GKR construction as pressure from packed
   words, univariate and binary-polynomial representations, PCS use, and an
   explicit cost model.

Primary papers and official specifications own external claims. Comparable
systems may inform representation choices, but they cannot establish source
correspondence or local correctness. Exact sources, revisions, locators, and
analogy limits belong in the source synthesis.

The package intentionally does not decide the general polynomial-commitment,
derived-Oracle, complete-argument, folding, recursion, endpoint, realization,
or evidence models. When the RAM case reaches a PCS boundary, it must expose
an exact typed dependency and stop at the next package's authority boundary.

## 3. Questions that must be answered

### Interaction and claims

- What exact object denotes the polynomial-evaluation claim at each round?
- Is claim evolution fully captured by the current finite claim/reduction
  graph, or does a source-faithful case require another semantic subject?
- Which public messages, challenges, side inputs, and residual obligations
  belong to one reduction occurrence?
- How are the final direct evaluation and the output residual relation
  distinguished from protocol acceptance and theorem truth?

### Composition and challenge use

- Can layered GKR be represented by finite authenticated unrolling and current
  composition maps while preserving the logical child Sumcheck boundary?
- Does one reused challenge need a new correlation primitive, or does the
  current challenge-use policy already express the source occurrence exactly?
- Can interleaving, verifier state, and layer transition be represented without
  runtime schedule generation or an opaque evaluator?

### Fiat--Shamir

- Does the current state/absorb/squeeze/advance algorithm surface represent the
  duplex transform without reducing it to a prefix hash?
- Which codecs, salt, framing, rate/capacity, permutation-call, retry, and proof
  serialization choices are construction identity, Analysis premises, or
  endpoint concerns?
- Does applying the transform to the constructive Sumcheck/GKR subjects need a
  new Core, a new challenge interpretation, or a checked prior construction?

### Algebra, setup, and resources

- Which field, polynomial, multilinear-extension, Boolean packing, RAM, and
  PCS assumptions are profile-local dependencies?
- Which round count, message degree, verifier work, communication, and memory
  bounds are semantic, theorem, or operational quantities?
- Can the modern case stop at a typed PCS contract without granting that
  contract commitment security or implementation authority?

## 4. Candidate classes

The comparison must include:

1. preserving the current Core claim/reduction and composition model;
2. completing owner views, contract profiles, or checked composition maps
   without changing existing subjects;
3. a targeted split between interaction, logical reduction, and child-call
   structure if constructive encodings prove the current boundary ambiguous;
4. a capability-expanding model only if at least two materially different
   cases require the same new law; and
5. an intentional v0 boundary when a capability is coherent but not necessary
   for the selected kernel.

No candidate may pass by storing a theorem name, accepting an opaque callback,
equating sample values after the fact, or letting its own witness author the
affirmative judgment.

## 5. Evidence contract

All four cases receive source-grounded anatomy and either a complete typed
abstract encoding or a decisive typed obstruction. Each representable encoding
must account for:

- parties, statement, witness, public parameters, and setup ownership;
- every message, challenge, check, claim, reduction, failure, and terminal;
- claim and value identities, occurrence order, guards, and causality;
- relation grounding and residual obligations;
- Fresh and applicable Fiat--Shamir subjects;
- exact resources and profile dependencies;
- representative well-formed negative mutations; and
- theorem, security, implementation, and family-support nonclaims.

Executable validation is promoted only when two plausible models remain
indistinguishable in prose or a claimed rejection boundary could be
self-fulfilling. Existing implementation fixtures are correspondence evidence,
not target authority.

## 7. Exit gate

The package closes only when:

1. every case reaches its assigned constructive depth or retains a decisive
   obstruction;
2. the complete source interaction can be reconstructed without an opaque
   evaluator, callback, or theorem assertion;
3. claim evolution, challenge use, subprotocol structure, relation grounding,
   and transcript behavior have exact owners;
4. every shared abstraction has both a positive inhabitant and a well-formed
   negative at its first intended boundary, while an obstructed case names the
   first missing field or law and rejects semantic workarounds;
5. any accepted semantic change is promoted to its durable owner and all
   affected completed witnesses are replayed at the necessary scope;
6. one frozen integrated review has no unresolved architecture blocker; and
7. the result states exact support, theorem, security, implementation, and
   downstream nonclaims.

Absence of a discovered defect is not closure. Conversely, an unimplemented
profile-local algorithm is not a reason to reopen the central architecture.

## 8. Risks and nonclaims

The selected cases may overfit public-coin algebraic protocols, and canonical
papers may leave serialization or commitment conventions implicit. Similar
words such as claim, reduction, state, round, or challenge do not prove that
two sources share a semantic object. Recent publication does not imply better
design.

This charter establishes no protocol correctness, soundness, zero knowledge,
knowledge extraction, Fiat--Shamir theorem applicability, asymptotic bound,
source correspondence, implementation conformance, supported family, semantic
freeze, migration schedule, or downstream activation.
