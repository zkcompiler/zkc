# Architecture Decision and Validation

## Selected laws

The durable profile selects three identified subject kinds:

1. a finite verifier-derived word program;
2. a finite logical query plan; and
3. an exact elaboration tying that plan to one admitted target Core.

Program routes are closed and exhaustive. Their source-read topology is fixed
before execution and cannot depend on an earlier source answer. Nested program
dependencies are acyclic, depth and leaf-read bounds are recomputed exactly,
and mathematically partial operations reach explicit semantic terminals.

The static checker derives the expected complete branch image and compares all
values, guards, source queries, answers, terminals, order, and maps. Missing,
extra, aliased, reordered, or kind-incompatible entries do not form an
affirmative result. The result is inert and grants no execution, theorem, or
compiler authority.

## Bounded executable evidence

The package forms five word programs and a five-site plan. Its static image has
62 events. Runtime witnesses cover:

- two DEEP-ALI-shaped quotient reads;
- STIR-shaped public-fill/source routing and nested folding;
- a three-source Circle-FRI-shaped batch combination; and
- a four-leaf WHIR-shaped grouped fold.

An independent module imports neither the reference model nor its evaluator.
It reproduces every output and exact ordered query trace from the fixed
fixture. Negative controls cover cycles, response-adaptive routing,
read-free answer-taint laundering through a prior-result argument,
nonexhaustive cases, false bounds, declassification, missing dependencies,
quotient collision, absent source entries, event and map mutation,
multiplicity loss, invented runtime/publication events, immutable snapshots,
and evaluator exhaustion. The independently authored nine-event activation
fixture is compared through a complete path-to-occurrence map: one causally
valid non-template ordering is admitted and checked, while answer-before-query
and operand-before-definition orderings are refused under stable codes.

This is finite executable evidence over a deliberately smaller reference
carrier. It does not instantiate or admit the complete target
`InteractiveCore`, settle one-case route guard normalization for K2 admission,
or establish a proof or implementation claim.

## Identity and dependency result

The profile directly imports only `pir.interaction`. Existing Interaction,
Fiat--Shamir, setup, commitment, Interface/Plan, and endpoint-source-view
profile bodies remain byte-identical. The new profile is an additive leaf in
the publication graph.

Program identity includes route, cases, algorithms, types, visibility, and
exact structural bounds. Plan identity includes program IDs, formal ports,
logical order, activation, and bindings. Elaboration identity includes the
plan, target Core, and complete maps. Runtime values, citations, evidence,
compiler routes, and evaluator work limits are excluded.

## Open source-correspondence questions

The structural profile deliberately leaves these questions open:

- the exact DEEP-ALI collision disposition and multipoint quotient convention;
- STIR's exact handling of conflicting out-of-domain or shifted assignments;
- equality between each bounded route and the corresponding paper definition;
- the relation between logical reads, source leaves, and profile-specific
  physical opening counts; and
- theorem applicability and quantitative loss for each complete protocol.

Relations owns the first four correspondence questions. Analysis owns theorem
applicability and property truth. None is a reason to invent a Core event.

## Reopening threshold

Reopen the satellite only for a source-faithful constructive case that requires
answer-adaptive query topology, a real public derived-word event, runtime-created
occurrences, authentication of the derived word itself rather than its source
Oracles, or a composition law that cannot consume the exact checked result.
Performance preference and API convenience are insufficient.
