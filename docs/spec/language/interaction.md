# Interaction and endpoint admission

An interaction describes which interface calls are permitted and how returned
replies change protocol phase. It is distinct from the runtime state carried
by a handler and from the information available to a participant. An endpoint
connects an actual source and input binding to a body satisfying the selected
interaction, return condition and call bound.

## Public families and semantic subjects

A public instance `p` selects a semantic environment: value domains, operation
meanings and module contracts. A relation-bearing construction may also supply:

```text
Statement p : Type
Witness p   : Type
R p         : Statement p → Witness p → Prop.
```

`R p x w` concerns the actual statement `x` and witness `w`. It is independent
of the protocol chosen to prove it. A service or module with no witness
relation need not be given one.

For an instance and role `ρ`, the following are different semantic subjects:

| Subject | Meaning |
|---|---|
| `P(p)` | The permitted interaction |
| `Aρ(p)` | The selected computation for a role |
| `Lρ(p)` | A plan realizing that computation under a specified contract |

These subjects need not be separate IRs or stages in a universal lowering
sequence. An honest computation additionally satisfies its declared honest
predicate. Interaction legality alone is not that predicate. A change of
protocol or construction needs a corresponding property argument, even if its
implementations use the same program representation.

Public parameters, runtime public inputs and private inputs are distinct.
Specialization on an invocation value retains its actual binding and disclosure
conditions. Private values and future challenges cannot silently become public
parameters. A family theorem quantifies over its declared parameter domain;
verification of finitely many instances proves neither that theorem nor a
family efficiency bound.

## Roles and phases

For an operation [signature](../core/execution.md#signatures) `Σ`, an
interaction `P` consists of:

```text
Role    : Type
Phase   : Type
owner   : Σ.Op → Role
enabled : Phase → Σ.Op → Prop
advance : (φ : Phase) → (o : Σ.Op) → Σ.Reply o → Phase
```

An operation includes its actual arguments and subject or session references.
`owner` identifies the interaction role associated with that operation.
`enabled` gives call legality at the current phase. `advance` gives the next
phase after an actual returned reply.

A stopping call has no reply and does not apply `advance`. Its runtime state
changes and events remain in the complete execution. Initial phase and initial
runtime-state conditions are explicit operands of an endpoint or execution
claim; one does not determine the other.

Reply types include the hostile values available at the interface. A predicate
about an honest prover's arithmetic does not justify removing adversarial
messages from a reply type. A bytes-to-values boundary decodes explicitly or
establishes the selected decoding contract for the actual supplied result,
including malformed-input behavior.

The operation's role label does not supply that role's knowledge, enforce
physical authentication or prove locality of a body. Those are separate
endpoint obligations.

## All-reply conformance

For `a : Proc Σ A` and phase `φ`, define:

```text
Conforms P (done x) φ   = True
Conforms P (halt r) φ   = True
Conforms P (call o k) φ = P.enabled φ o ∧
                          ∀ reply, Conforms P (k reply) (P.advance φ o reply)
```

The quantifier covers every value of `Σ.Reply o`. It is not restricted to
replies reachable from one honest handler or one sampled run. A call must be
enabled even when the actual handler stops on that invocation.

Finite returned-response histories are generated by staying at the same body
and phase, or by moving from `call o k, φ` to
`k reply, P.advance φ o reply` and continuing with another finite history.
Conformance is preserved along these histories.

Instrumenting an actual execution with its call-entry phase establishes that
every invoked operation of a conforming body is enabled at that recorded phase,
including an invocation that stops. This is a property of the actual call
history, not only of calls that produce user-visible events.

Conformance describes legal calls. A body that stops immediately conforms;
conformance therefore implies neither successful completion nor acceptance,
honest arithmetic, input access or a public call bound.

## Returning postconditions

Let `Q : A → P.Phase → Prop`. Define:

```text
Returns P Q (done x) φ   = Q x φ
Returns P Q (halt r) φ   = True
Returns P Q (call o k) φ = ∀ reply, Returns P Q (k reply) (P.advance φ o reply)
```

This is partial correctness of returning paths over all typed replies.
Stopping paths satisfy it without producing a value or satisfying `Q` at their
final phase. Their stop, state and events remain observable through execution.

If `Returns P Q a φ` and an actual phase-instrumented execution of `a` returns
`x`, then `Q x ψ` holds for its actual final instrumented phase `ψ`. This law
does not require a fabricated phase transition after a stopping call.

## Phase-safe sequencing

For `a : Proc Σ A`, `k : A → Proc Σ B`, entry phase `φ`, and intermediate
postcondition `Q : A → P.Phase → Prop`, the conformance rule is:

```text
Conforms P a φ
Returns P Q a φ
∀ x ψ, Q x ψ → Conforms P (k x) ψ
───────────────────────────────────────
Conforms P (a.bind k) φ
```

For `R : B → P.Phase → Prop`, returning postconditions compose by:

```text
Returns P Q a φ
∀ x ψ, Q x ψ → Returns P R (k x) ψ
───────────────────────────────────────
Returns P R (a.bind k) φ
```

The suffix premise uses the first body's returned value and phase. Proving the
suffix legal at an unrelated entry phase does not supply that premise.
The second rule is independent of conformance; a returning assertion alone
does not prove legality of the calls producing the return.

Module preconditions, state ownership and failure effects require their
[complete-result contracts](../core/contracts.md). They are not supplied by a
phase postcondition alone.

## Bounded repetition

Let `step : A → Proc Σ A` and `Inv : A → P.Phase → Prop`. Suppose, for every
`x` and `ψ` satisfying `Inv x ψ`:

```text
Conforms P (step x) ψ
Returns P Inv (step x) ψ.
```

Then for every natural count `n` and initial `Inv x φ`:

```text
Conforms P (repeatN n step x) φ ∧
Returns P Inv (repeatN n step x) φ.
```

The count zero performs no step and retains the initial invariant. The rule
retains an actual accumulator/phase relation between all returned iterations.
It does not convert that relation into a checker accepting every valid loop.
The [structural call-bound law](programs.md#structural-call-bounds) is independent;
public admission additionally establishes the selected count's public origin.

## Local information

A deterministic local strategy has type:

```text
Viewρ → Memoryρ → Decisionρ × Memoryρ.
```

It acts on the role's permitted view and retained memory and obeys its actual
interface restrictions. Global phase, another role's private input and hidden
provider state are not implicit additional arguments. A local implementation
claim establishes how the selected inputs and state yield this view.

Let `view : World → View` and `required : World → Action`, where `Action`
contains everything the claim requires the adapter to select, including code,
arguments and memory if applicable. If a deterministic adapter
`f : View → Action` satisfies `f (view w) = required w` for every world, then:

```text
view w = view v ⇒ required w = required v.
```

Two equal-view worlds requiring different actions rule out every such adapter.
Choosing a hidden default locally does not repair this obstruction. The
interaction must change or the adapter must receive additional permitted
information.

The equality condition alone does not specify executable selection of a world
from a view. One sufficient construction supplies an explicit representative
`represent : View → World` satisfying
`view (represent (view w)) = view w` for every `w`. If `required` is constant on
equal-view worlds, then `f v = required (represent v)` has the required action
on all actual views. The construction states its representative and laws;
it is not a total global-to-local protocol generator.

## Endpoint admission

A frontend `F` for signature `Σ`, role type `Role` and result type `A` fixes:

```text
Source    : Type
Binding   : Type
inputs    : Source → Binding → Role → Prop
elaborate : Source → Binding → Role → Option (Proc Σ A).
```

For admission under `P`, its role type is `P.Role`.

The frontend's input predicate states its actual input and capture obligation.
For a typed source, [ordered binding and permitted reads](inputs.md) can supply
this interpretation. A frontend claiming locality MUST connect that predicate
and its elaboration to actual permitted reads and source selection. An arbitrary
true predicate is not evidence of that connection.

An endpoint contract for `P` and `A` consists of:

```text
initialPhase : P.Phase
publicBound  : Nat
returned     : A → P.Phase → Prop.
```

For source `src`, binding `β`, actor `ρ`, contract `C` and body `a`, admission
is the conjunction:

```text
F.elaborate src β ρ = some a
F.inputs src β ρ
Conforms P a C.initialPhase
Within C.publicBound a
Returns P C.returned a C.initialPhase.
```

All operands refer to the same selected instance, source, binding, actor and
body. Two admissions with the same frontend, source, binding and actor have
the same elaborated body. Applying execution refinement to those bodies still
requires its actual handler laws and related initial states.

Admission is a mathematical predicate independent of the method establishing
it. A generated endpoint supplies a justified projection; a supplied endpoint
supplies correspondence to its selected source. The conjunction does not prove
an arbitrary input predicate adequate, authenticate a provider or synthesize a
local strategy. An honest-role claim also supplies its honest computational
predicate in addition to conformance. That predicate does not narrow the
adversary's available replies or strategies.

The [finite phase analysis](../profiles/compiler/finite-phases.md#abstract-phase-policy)
is one sound, sufficient way to establish the phase components. It does not
define their full semantic domain.

## Atomic sessions

Let `Session` have decidable equality. Each session `s` has a signature `Σs`
and interaction `Ps`. The combined signature and phase space are:

```text
Op       = (s : Session, o : Σs.Op)
Reply(s,o) = Σs.Reply o
Role     = (s : Session, ρ : Ps.Role)
Phase    = (s : Session) → Ps.Phase.
```

The role and permission of `(s,o)` are `(s, Ps.owner o)` and
`Ps.enabled (Φ s) o`. A returned reply updates only the selected phase:

```text
advance Φ (s,o) reply = Φ[s ↦ Ps.advance (Φ s) o reply].
```

The phase at `s` is the selected interaction's next phase; every distinct
session retains its previous phase. A stopping invocation performs no such
reply transition. Actual calls of a conforming combined body satisfy the
selected session's permission at their recorded entry phase.

Runtime state can remain shared across sessions. Separate phase indices imply
neither independent providers nor commuting actions or independent randomness.
Session-role tags do not determine physical principals or their views. A body
has its separately established finite bound even if the session index type is
infinite.

The selected [atomic execution envelope](../conventions.md#execution-envelope)
provides no implicit fairness, channel delivery, asynchronous projection or
concurrent-security theorem.

## Invocation-selected members

[Family ingress](../profiles/source/families.md) selects configuration and bound
inputs from the actual invocation. Its complete result precedes the selected
member. Admission and bounds are per member; local knowledge determines whether
each role can select its required behavior. Neither a shared abstract parameter
nor an honest encoding theorem covers arbitrary incoming data or later choice.
