# Architecture of source-issued security claims

A security claim needs two kinds of evidence. The first identifies the program, role, stage, view and local functions denoted by the source. The second proves a property of their executions. A kernel-checked proof can establish exactly the wrong claim if the compiler chooses a different protocol specialization before Lean sees the target. The architecture should make that first choice inspectable and test it independently.

## Boundaries in the current implementation

| Owner | What it determines | Evidence at the boundary |
| --- | --- | --- |
| Source frontend | The selected entry scheme, closed protocol instance, defining contract, public operands, event fields and the functions selected by the clause | Ordinary name and static resolution, ordinary body elaboration, source locations and checks against emitted ports and addresses |
| Core | The well-typed program admitted from the stored form, the projection for each role and its process semantics | Three readbacks for the group fork. They connect the actual protocol, relation and extractor to their respective admissions |
| Formal semantics | What an execution, a fork, an observation or a probability means | Exact returning transcripts, stateful effects and finite expectation all refer to the same Core process. The bind theorem for process interpretation supplies their structural composition |
| Family mathematics | Why the observed equations imply the requested property | One group-action extraction lemma covers the two group examples. A shared reduction theorem covers the pair and gate rounds with different collision laws |
| Proof automation and companions | How to construct evidence for a target fixed by the preceding layers | The group strategy walks the projection and checks the calculation against both local function meanings. A companion can use the compiled target directly |

Source parsing, static resolution, elaboration and lowering are trusted compiler operations. Admission and readback relate stored Core to its typed meaning. The independent consumer applies the public theorem to three successful admissions and requests a fork over the actual role and function executions. Mutating the theorem to `True` must fail at that consumer. Kernel replay checks the logical declarations in the two baseline modules and their project import closures. ## Which duplication to remove

**Represent the author's inputs once.** For a supported group protocol, the extractor sees a sized sequence of generated `Run` records. Its nominal identity belongs to the closed protocol instance. Source typing owns collection length, indexing and field projection. The record stores a field for each of the three public events in their source order. An unnamed event uses its ordinal selector. A local binder may have a different name from its site. Import-fixed specialization, public context and role designation belong to this boundary too. A `G2` run cannot justify extraction for a `G1` scheme. [Generated members](../language/LANGUAGE.md#8-generated-members) · [Contract binding](../lean/compiler/Zkc/Frontend/Written/Contract.lean)

**Share the instruction rule at the level where it is valid.** A guard private to the prover disappears from the verifier projection. A shared guard constrains every accepting verifier execution. Exact traces and stateful probabilities can share structural recursion and bind. They need different effect rules and return observations. For example, finite expectation uses each reply's weight and threads the service state. Its monotonicity theorem only needs an inequality on returns reachable with positive weight. A single Boolean acceptance check would lose that distinction. [Projection rules](../lean/formal/Zkc/Formal/Written/Steps.lean) · [Process interpretation](../lean/formal/Zkc/Formal/ProcessJudgment.lean) · [Finite expectation](../lean/formal/Zkc/Formal/Interactive/Experiment.lean)

Clients can rewrite expectations with `expect_bind`, `expect_done`, `expect_halt` and `expect_call`. These equations keep a proof about the experiment independent of how the shared interpreter recurses.

**Keep two representations when their agreement is the evidence.** Stored and typed Core have different consumers. Readback checks their correspondence. The short relation and extractor calculations are optional inputs to the automatic group proof. Both must agree with the admitted local functions on every input, including a failing division. The public result and the companion entry point use the compiled executions. A second translation with no such agreement would introduce a second source of truth. [Generated declarations](../lean/compiler/Zkc/Frontend/Written/Export.lean) · [Function interpretation](../lean/formal/Zkc/Formal/Written/FunctionMeaning.lean)

**Quantify laws over the operations a theorem uses.** For a reduction of length `n`, the round theorem accepts a polynomial interpretation at each remaining depth in `Fin n`. Its root bound uses just that depth and its predecessor. There is a concrete four-round claim with a valid polynomial at every executed round and inconsistent requirements at the next depth. Requiring those extra laws would exclude this instance without improving the bound. At a world read, the owner operation has the actual listener list, so its grant must match this list. The recorded owner event has already erased the list and admits an existential statement about the original grant. [Reduction theorem](../lean/formal/Zkc/Formal/Interactive/RoundFamily.lean) · [Four-round control](../lean/formal/Zkc/Tests/Formal/Interactive.lean) · [World observations](../lean/formal/Zkc/Formal/WorldObservation.lean)

The round interpretation has one representation for both kinds of client. A Sumcheck proof can supply its formula at every natural depth. A GKR proof can supply a polynomial for each of its four depths. Restricting the first proof to the executed indices or passing the remaining indices to a recursive call preserves the same boundary function, evaluation and collision proof. [Sumcheck interpretation](../lean/formal/Zkc/Formal/Interactive/PairSequence.lean) · [Gate interpretation](../lean/formal/Zkc/Formal/Interactive/GateSequence.lean)

## Larger changes and their acceptance criteria

| Order | Design change | First evidence that would justify adoption |
| --- | --- | --- |
| 1 | Move closed contract binding and generated views into ordinary frontend typing. Give a selected claim an explicit stage, deciding role, ordered ports, typed event fields, local function identities and their source locations. Make both the exporter and future property applications consume that same result. | Bind Schnorr and Chaum–Pedersen through ordinary module elaboration. Preserve the independent three-admission consumer, the specialization and role refusals, and the collection operations. Then accept a scheme with public context and demonstrate that the context occurs in the public theorem. |
| 2 | Derive the optional calculation or its verification conditions from the admitted typed function. Keep the per-operation laws in Lean and the public target available to companions. Use the existing separate calculation as a comparison while migrating. | An extractor using a local alias and a legitimate sequence operation, a restricted inverse that can stop, and a different family using the same structural rules. Check successful and stopped executions. Measure generated text, checking time and memory across increasing program sizes before adopting a new renderer or cache. |
| 3 | Bind a written oracle spot check to a concrete stateful service. The send fixes the table. The query and opening carry typed positions, claims, payloads, principals and recipients. Prove that the joint execution agrees with the authorized role observations and state transitions. | An honest source opening returns. Changing the table after the send or changing the opened row cannot produce the same accepting observation. Test a private read and a forged listener list. An effect-level observer alone cannot establish the theorem about the enclosing program. |
| 4 | Connect the existing finite-state expectation to an external probability semantics on the shared fragment. Preserve missing mass, stopping and state-dependent challenges. Extend the subject to a transformed stage only after it binds the actual stage program and service. | Prove agreement on a stateful finite service and on a stopped branch. Then use the bridge in a source-issued bound. A Fiat–Shamir or simulation claim also needs its own transformation or distributional theorem. |

Steps 1 and 2 address growth in the current group proof path. The spot check exercises an independent protocol family and gives a concrete requirement for step 4. Shared Core bind and projection rules can support all four steps. Library properties should take the typed subject as an argument. For a new security property, a Lean definition and a companion can supply its mathematics. A source language extension is justified when the author needs to identify an input, scope or effect that the current language cannot express. Lean's verification-condition generator can compose registered rules and consume supplied loop invariants. The companion still provides the invariant or the mathematical law that makes the verification conditions true. [Lean verification-condition generation](https://lean-lang.org/doc/tutorials/latest/vcgen/)

### Round identity and repeated code

A written event identifies a declaration, event and part. Its realization identifies the instantiated program, enclosing block path and instruction. Layout and charging refer to the former. Execution and linked function selection refer to the latter. A repeated family can share a typed round description while carrying each instance's captures, result types and operation references. Before changing physical keys or emitting one parameterized body, move attachment lookup and interpretation dispatch to full realizations. Check both the stepped reduction and the enclosing uniform GKR loop, with a mutation that exchanges two different callees. Whole-GKR soundness also requires the caller's reached state, wiring, continuation and terminal evaluation. ### Adoption and validation

Run the compiler, interactive and written gates for changes that cross these boundaries. The lightweight CI checks the public tree, documentation and Unicode tables. Adding proof validation to CI requires a runner and cache budget for the pinned toolchain and a persistent report of which roots were checked. The existing three local gates provide reproducible commands and separate axiom policies for this decision. [Development and audits](development.md)
